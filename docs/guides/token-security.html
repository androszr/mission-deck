Security one-pager

Access tokens and .env files - how not to leak them

One stolen Jira token, API key or personal access token opens the door to your tools, data and systems. This page is the full set of rules for everybody on the team, whatever their role.

Why it matters

Bots scan public commits in real time: a key pushed to a public repository is typically tried within minutes. Breaches based on stolen credentials are among the most common and the slowest to be detected. A leaked token is not a hypothetical risk.

Good practice

1. Keep tokens only in safe places. A password manager or vault (Mission Deck reads tokens from Bitwarden) - never documents, notes, chat messages or shared files.
2. A .env file never goes into a repository. Mission Deck's .env holds configuration only, never a secret, and is gitignored. Keep it that way.
3. Do not copy tokens into files and documents. A token pasted into a wiki page, a spreadsheet or a slide lives there forever and is readable by everybody with access to that file.
4. Rotate tokens regularly. Set an expiry date (12 months at most) and rotate earlier whenever the team changes. A token without an expiry is security debt.
5. Grant the smallest scope. Pick only the permissions you actually need: read-only instead of full access, one project instead of the whole organisation.
6. Use a vault. One safe place for every token and key makes them easy to revoke and rotate.

A token leaked? Act now

Every minute counts. 1) Revoke the token in the settings of the service it came from (your Git host, Jira, Figma, ...). 2) Create a new one with the minimal scope and replace it everywhere it was used. 3) Tell your team lead and whoever handles security - even if "probably nobody saw it". 4) Deleting the chat message is NOT enough - the token may already have been copied or indexed.
