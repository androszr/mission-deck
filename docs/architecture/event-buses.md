# Event buses and the module sync bar

Detail moved out of `CLAUDE.md` (section "Architecture") so the file Claude Code loads on every turn stays under its size limit. `CLAUDE.md` keeps the rules; this file keeps the reasoning, the incidents and the measurements behind them. Add new detail HERE and at most one line to `CLAUDE.md`.

Everything the browser paints from a credential is DERIVED state, so opening the vault must never need an F5: a successful `POST /api/bitwarden/unlock` or `/api/bitwarden/refresh-secrets` announces itself on one bus - `js/secrets-events.js`, event `cockpit:secrets-changed` - and the top bar (avatar, "Active" chip, the pill, the sync status), the Settings panels that read a token (Bitwarden card, Keys cards, sync, Tools, the Modules catalog), the onboarding wizard and the "GitLab activity" view re-derive themselves from it - that last one fetches at init and repaints from a module-level cache, so without the bus a vault opened after its first entry left "no token" on screen for the whole session. A third module rather than direct calls, because `js/settings.js` already imports `js/topbar.js` while the top bar dynamic-imports settings for the modal - a second static edge would close a cycle - and because the unlock can be started from any of the three. The event carries no payload worth trusting: every listener re-fetches its own endpoint, on the same rule `js/state.js` states for the shell. No cache-bypass parameter is needed for the identity and activity endpoints because their server caches are keyed by the TOKEN (`_gitlabIdentityCache`, `_gitlabActivityCountCache`), so a credential that just appeared is a MISS; `/api/tools/status` is the one exception and gets `refresh: true`. Settings and the wizard skip the work while their view is hidden - the next entry re-renders in full anyway. That bus is also why `_openBitwardenModal` takes no success callback any more. The modal's fourth step keys its two forms on `sessionOpen`, never on `hasSecrets`: with a session this process holds it shows the collection field plus "Refresh secrets", and "Save" is a `POST /api/bitwarden/refresh-secrets` with `collectionName` in the body - the open session re-reads the new collection, no password and no restart - while without one it shows the same field over the password form, so the collection can be changed in every state. It used to vanish the moment the vault was unlocked, and a restart did not bring it back, because the handoff carries the session across. A name that matches no collection is never persisted (`_bwSettleCollectionName` puts the previous one back) and the answer lists the collections the vault does have; a `bw list` that could not run is `listFailed`, not "not found". And a session bw stops honouring - `bw status` under the handed-over key answers `locked`, and `bw list collections` under it exits 0 with `[]` (measured) - is dropped by the status handler and by the refresh preflight (`_bwSessionStillOpen`), so `sessionOpen` turns false and the modal asks for the password instead of blaming the collection; the tokens in the heap stay, because they are still valid on their own. `_loadBwCollectionTokens` also clears the previously vault-loaded keys once the new collection has been read, so a switch does not leave the old collection's tokens in `process.env`. Covered by `tests/test_secrets_events.mjs`. The team DATA has the same problem one axis over and the same answer: a pull rewrites the plaintext tree under a page that is already painted, and the sync modal sits ON TOP of that page, so seeing the new data meant F5 with the modal still open. `js/data-events.js` (event `cockpit:data-changed`) is that second bus, and unlike the secrets one it has exactly ONE listener, because nothing opts in: a view or a module written tomorrow refreshes without a line of its own. It is emitted only on SUCCESS and from the two finish paths every sync funnels through - `_finish` in `js/sub-repo-sync-stream.js` (the sync center, the onboarding wizard) and `runDataTierSync` in `js/data-tier-0-sync.js` (Settings > System) - plus the ops that rewrite the tree without a stream, which all go through the one `_mutating` wrapper there (`decrypt`, `clear-dir`, `discard-local-changes`, and inline `write-resolved` / `push`); the read-only `conflict-diff` deliberately does not. The listener is the ROUTER, because `js/app.js` is the one place that knows which view is on screen. `refreshActiveView()` re-reads the shared roster (`loadTeamDirectory(true)`) BEFORE anything repaints, then takes one of two paths. A CORE view is audited in this repository, so the core knows whether its renderer fetches what it paints - most do, so it is repainted and keeps its scroll and open tab; the one that paints from a module-level cache says so with `refresh` in `VIEW_REGISTRY` (`refreshAcademyData`). An INSTALLED MODULE is somebody else's code, gitignored and never read here, so the core cannot know what it cached and asking module authors for a hook would leave every view that forgets it stale. Those are RE-ENTERED instead, which is what an F5 did for the view minus the page: the outgoing instance's cleanup runs, the section is restored, the module file is re-imported as a fresh instance and init plus render run again. Three details are load-bearing. A fresh instance can only come from a NEW URL (`import()` is memoized per URL), so `importFn` takes a cache-bust suffix and `reloadViewModule` bumps one GLOBAL generation - global because a hub module backs several views off one file, and all of them are dropped together so they re-import at the same generation and stay ONE instance. Only an entry carrying `moduleId` (stamped by `js/module-host.js`) is reloadable; a core view keeps the instance it booted with. And the section is restored from a PRISTINE snapshot taken on the first navigation into the view, never from a clone of what is on screen: `cloneNode` copies attributes but not listeners, and the usual way to make a delegated listener idempotent is a marker attribute on the container (`root.dataset.sklWired` in one installed module) - the clone carried the marker, the incoming instance read "already wired", bound nothing, and the view repainted and then answered no clicks. Re-running init is allowed ONLY on that path, because the instance behind it is new; anywhere else it would re-register listeners the cleanup registry has already consumed. Two consequences are deliberate and written down rather than rediscovered. Only the ENTRY file is busted: a relative specifier inside it resolves against the base URL WITHOUT the query, so a module's siblings (`<id>-lib.js`) stay one shared instance across every generation - which is what stops a hub module's helpers forking, and which is why team data must never be cached in a sibling, where the reload would not clear it (`modules-template/README.md` states that rule for module authors). And each generation leaves the previous instance in the browser's module map, which has no eviction - one retained namespace per module per sync, bounded because a sync is a deliberate action and not a loop. The reload costs the view's transient state, so a module that would rather keep it exports `onDataChanged()` and refreshes itself; the adapter reports whether it handled the call, and no hook, or a hook that throws, falls through to the reload, because a stale view is the worse outcome. That is an OPT-OUT of the reload, never a prerequisite for being refreshed. Overlapping events cost one repaint, not one each. Covered by `tests/test_data_events.mjs`. A module view with a non-empty `dataRepos` gets one more thing from the core for free: a read-only "module sync bar" (`js/module-sync-bar.js`, `paintModuleSyncBar`), a `ds-callout` `js/module-host.js` injects as a SIBLING between the section's `.page-header` and its `.view-data` root, so a module's own `innerHTML =` can never wipe it. It answers one question - "is what I see up to date?" - from the existing `POST /api/sync-overview/refresh` (client-throttled to the server's own 60 s TTL) and `GET /api/sync-modules`, painted through the pure `moduleSyncBarState()` (`js/sync-center-helpers.js`), and its one button opens the same "Sync" modal through a dynamic `import('./sync-center-modal.js')` - it never pushes, pulls or decrypts itself. It paints from BOTH of `js/module-host.js`'s adapters (the render path on every navigation, the data-hook path on every accepted `onDataChanged()`), which is what makes it correct after navigation, after a reload AND after a module's own opt-out with no listener of its own; a module-level `_dirty` flag set by its own `onDataChanged()` subscription forces the next `refreshSyncModules()` call past the CLIENT memo the same way a moved remote ref forces it past the server one. The bar ships its own `data-skel="1"` skeleton, so `_showLazyLoader`'s "stand down for any skeleton" check (`js/app.js`) had to narrow from `.ds-skeleton` to `.ds-skeleton:not(.msb-skel)` - otherwise the bar alone would have silenced the mascot loading scene for the module's own import on every view that carries one. Two server changes back it: `_repoRefreshRemote` now calls `_invalidateSyncModules(d.id)` right after `resetCheckCache()`, so "refresh then read" never answers with the pre-fetch count; and `_syncModulesForRepo` resolves an upstream `.enc` name through `_resolveRemoteAheadNames`/`_repoUpstreamPathForMirrorFile` (a bounded, batched `git show @{upstream}:<name>` plus decrypt) before classifying it, so a teammate's brand-new file is attributed to its module instead of falling into "Cockpit Core" for having no local plaintext copy yet.
