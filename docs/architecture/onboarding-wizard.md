# Onboarding wizard

Detail moved out of `CLAUDE.md` (section "Architecture") so the file Claude Code loads on every turn stays under its size limit. `CLAUDE.md` keeps the rules; this file keeps the reasoning, the incidents and the measurements behind them. Add new detail HERE and at most one line to `CLAUDE.md`.

The first-run guide is `#view-onboarding-wizard` (`js/onboarding-wizard.js`), reached from the dashboard tile, from the rail item "Start here" pinned above Settings, and from the browser cockpit auto-opens when nothing is configured yet. Seven cards, one per step: environment (`/api/tools/status`), Bitwarden, the APP project token (`COCKPIT_APP_TOKEN` alone), encryption keys, then the data-tier-0 card - which carries `COCKPIT_DATA_TOKEN` next to the clone button it unlocks, so a data source's three prerequisites (key, token, clone) sit in one card - the update check, then training. A token badge distinguishes a CLOSED vault from a missing entry: a locked vault loads nothing, so "Missing" there would be a claim the client cannot back up. Saving a key re-decrypts the sources it names through `pull-stream` (there is no decrypt-only op), but only those already cloned AND with nothing unsent - `plaintextDirty` or `filesToSend > 0` on the `/api/sync-overview` row skips the source, because a pull decrypts the mirror over the plaintext tree the app writes to. It is a CORE view, not a module, and deliberately gets NO `HUB_FLYOUT` entry - the wizard is not a hub, and `HUB_FLYOUT` carries exactly the eight hubs `js/core-hubs.mjs` declares. That is exactly why its rail item is STATIC markup in `index.html` rather than config: a `HUB_FLYOUT` key would make `js/app.js` treat the id as a hub and redirect `#onboarding-wizard` to the dashboard, so the item would land on the wrong view. It sits after `.sidebar-spacer`, which is the pinned bottom group; module items are injected BEFORE the spacer (`js/module-host.js` `insertBefore`), so the divider above that group hangs on `.sidebar-spacer + .sidebar-item` and a second pinned item never draws two lines. Every badge is derived on each entry from the vault, the key file and the clone on disk, so nothing about progress is stored server-side and the view is re-enterable. Which is also why the first paint is a SKELETON and not empty containers: five probes fan out at once, so `_buildHtml` ships `ds-skeleton` bars inside the real `.obw-repo-row` / `.ds-callout` / `.obw-bw-status` boxes and every card keeps its finished height from the first frame (measured card-for-card; only step 7 grows, and only on a cockpit that is already configured, because a completion callout cannot be predicted from a pending sentence). Two rules hold it up. A painter must overwrite its container UNCONDITIONALLY - `_paintStep2` skipped an unanswered `/api/bitwarden/status`, which left that one bar pulsing for good, so it now says so instead. And a bar tops its line box up with MARGINS only inside a padded box (`.obw-repo-row`, `.obw-bw-status`); in a plain block those margins collapse straight out and reserve nothing, which is why step 7's placeholder carries padding. The row itself needs no arithmetic - `.ds-badge` is taller than its label, so a 24px badge bar alone holds the row. The two buttons whose enabled state comes from data start `disabled`, because during the skeleton phase there is no answer to enable them from. Two endpoints back the key step: `GET /api/settings/encryption-status` (one row per encrypted repo, `repos[].id` being the ONLY allowed-id list the client may use - never a copy in the browser) and `POST /api/settings/encryption-key` (`checkOrigin`, validated against `KNOWN_REPO_IDS`, `saveRepoKey` behind a chain lock). Neither ever returns key material. Covered by `tests/test_onboarding_wizard.mjs` and `tests/test_api_encryption_key.js` - the latter never exercises a successful save, because the handler writes the real `.encryption-key`; the write is sandboxed in `tests/test_crypto_sync.mjs` instead.
