# End of day / Good morning

Detail moved out of `CLAUDE.md` (section "End of day / Good morning") so the file Claude Code loads on every turn stays under its size limit. `CLAUDE.md` keeps the rules; this file keeps the reasoning, the incidents and the measurements behind them. Add new detail HERE and at most one line to `CLAUDE.md`.

The top bar carries ONE day-cycle pill (`#topbar-daycycle-root`), never two: `dayCycleMode(rows)` in `js/day-cycle-helpers.mjs` answers `morning` when ANY `/api/sync-overview` row has a `wrappedUpAt`, and `wrapup` otherwise - a mixed state resolves to `morning` on purpose, because getting the data back is what unblocks work. `refreshDayCycleButton()` repaints the slot after a wrap-up that cleared something and after a successful decrypt, so the button flips back without an F5 and without a poll of its own. Evening sends what is unsent through the existing `push-stream` and then calls `POST /api/data/<repoId>/clear-plaintext`; morning is `POST /api/data/<repoId>/decrypt`, which already existed and needed no new route. Both pills are an explicit exception to the rule at the top of `js/topbar.js` (a control earns a slot only if it is needed on every view AND has an endpoint in BUILD-CONTRACT): the wipe is a whole-machine action, so it belongs nowhere narrower than the bar.

`clear-plaintext` is the one operation here that can destroy data, and the invariant is not negotiable: the eligibility probe (`plaintextAheadOfMirror` with `added === 0 && changed === 0`, a FULL run - `stopAtFirst` returns early and leaves the counts inexact) plus a clone plus a key are computed in the SAME call, under the SAME `d.lockFn` + `withRepoFileLock` pair, immediately before the `fs.rmSync`, and always against `d.plainDir`, never `d.dir` - the mirror is the only remaining copy at that moment. `key-missing` has no override and no `force` flag, because a source whose key never arrived may hold plaintext the mirror never received. A failed PUSH does not block the wipe and a failed ENCRYPT does: once encrypt+commit succeeded the work is in the local mirror and a decrypt recovers it, so refusing on a flaky VPN would only mean the cleanup never happens. It is `generic: true` for every source under the same test the rest of `DATA_REPO_OPERATIONS` uses - it never calls `encryptFn`. The wipe is idempotent: an already-empty tree answers `{ ok: true, alreadyEmpty: true }`, not an error.

The gitignored `data/day-cycle-state.json` (tmp+rename, memory-only under `IS_TEST_MODE`, same discipline as `data/academy-sync.json`) exists for exactly two reasons and must not grow a third. It gives the wiped state a name of its own - `decrypted: false` alone cannot tell "emptied last night" from "cloned before the key existed", and the two deserve different English copy (the separation is not perfect: a cloned-but-never-decrypted source hits the idempotent `alreadyEmpty` path and gets a mark too, which costs one badge word and no behaviour, since both offer the same decrypt). Its second job is the one that matters: surviving the half-populated tree. One write into an emptied plaintext directory (a Academy `verify-step`, say) makes `_dirNonEmptyIgnoringJunk` true and `mirrorOverlap` non-zero, so `_repoDecryptedState` reports `decrypted: true` on a tree that is 99% empty and the morning modal would stop offering the decrypt that fixes it. It is deliberately NOT a write blocker - `encryptTree`'s own guards (`mirrorOverlap === 0` and the 30%/50-file ratio) are the last line, and blocking writes was never asked for. A successful decrypt clears the mark; `_runAutoSyncCycle` reads it and skips with `wrapped-up` before taking any lock, because without that gate every interval would end in `encrypt-destructive` in the log forever. "Already greeted you today" is `localStorage` (`cockpit.dayCycle.greetedOn`), never server state.

`POST /api/settings/shutdown` is `handleSettingsRestart` minus the respawn - `checkOrigin`, 202 `{ status: 'stopping' }`, the same `TEST_DISABLE_RESTART` / `IS_TEST_MODE` bramka (without it the API suite kills its own server mid-run), then `server.close()` into the existing `_gracefulExit(0)`, which already removes the pid file. No `lsof`, no `kill -9`, no `taskkill`: those would also kill whatever else happens to hold the port, and the Critical rules forbid them anyway. `scripts/stop-server.js` stays untouched and remains the terminal's way in. The button lives ONLY in the wrap-up modal's summary state - killing the process mid-run would leave a half-wiped tree and possibly a held repo lock, which is the exact state this feature exists to prevent - and closing the process is also what shuts the Bitwarden safe, since a restart hands the session across but an exit does not.

Both modals are `ds-modal--lg` and cap `.day-cycle-modal .ds-modal-body` with `max-height` + `overflow-y: auto`: `.ds-modal-overlay` centres without `overflow`, so a modal taller than the window is clipped at both ends with no way to scroll to it, and eight source rows plus an illustration reach that height on an ordinary laptop. The shared `css/ds.css` is not touched for this - a fix there would change every modal in the app. And an illustration in a modal that STAYS OPEN must be a looping mascot pose, never a one-shot `forwards` animation: a pose that leaves the frame and holds its final keyframe, which left a blank 236px box under the heading. It now appears only on the post-shutdown farewell screen, where disappearing is the point; the confirm and summary screens use the looping `pip-sleeping` pose, and the morning modal uses a pose whose last keyframe is its resting position. Covered by `tests/test_day_cycle_helpers.mjs`, `tests/test_api_data_day_cycle.js`, the `wrapUpClearEligibility` block in `tests/test_server_helpers.mjs` and the `wrappedUpAt` cases in `tests/test_sync_center_helpers.mjs`.
