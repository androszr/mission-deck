# Team directory, Users and Tools

Detail moved out of `CLAUDE.md` (section "Architecture") so the file Claude Code loads on every turn stays under its size limit. `CLAUDE.md` keeps the rules; this file keeps the reasoning, the incidents and the measurements behind them. Add new detail HERE and at most one line to `CLAUDE.md`.

The team directory lives in that same data repo under `team/`: `team-members.json` (`id`, `first_name`, `last_name`, `role`, `team`, `email`, `avatar`) plus `team/avatars/` with one photo per person, both built by `node scripts/build-team-directory.js` and served statically, so no endpoint fronts them. `js/team-directory.js` is the ONE resolver every view uses - `memberByName` matches a person through diacritics, case, a contract-code prefix (`BS`, `I2S`, ...), a parenthesised suffix and the surname-first order, `memberAvatarUrl` turns a record into a photo URL. A fresh clone has no `team/` folder, so the directory resolves empty and every caller falls back to initials; the top bar avatar is the first consumer (team photo > GitLab avatar > initials). Settings > Users edits the same two files through `/api/team/*` (`js/settings-uzytkownicy.js`): a searchable card grid, one modal per person and a photo upload whose file name is ALWAYS derived server-side from the person's slug and whose format comes from the magic bytes, never from the request - a client never names a file on this disk. `node scripts/build-team-directory.js` is the one-time importer that seeds the directory from another cockpit's roster; after that the tab is the place to edit it, because a re-run rewrites what the tab wrote.

Settings > Tools (`js/settings-narzedzia.js`) is the environment check: `GET /api/tools/status` probes twelve things this cockpit leans on - Node/npm against the `engines` range, git, Python (`py -3` then `python` on Windows, `python3` then `python` elsewhere - the command that answers differs per system and the card names it), the Bitwarden CLI (version plus lock state, never the person behind it), the Claude Code CLI, the in-app terminal (`pty && wss`, read for free), the `.mcp.json` entries, the pinned `@playwright/mcp` package, the Chromium builds on disk, the gitnexus CLI and whether `.gitnexus/meta.json` still matches HEAD. Probes run in parallel behind a 60 s cache (`?refresh=1` bypasses it), the answer is ALWAYS 200 because "not installed" is an answer, and the payload is facts only plus `platform` (process.platform) - every English label and fix command lives in the client module, and the runtime remedies (node, npm, git, python) are keyed on that `platform`: winget on Windows, Homebrew on macOS. Two Windows rules hold the whole tools section up. A shell goes ONLY to the `.cmd` shims (`_toolShell`): Node refuses to spawn them without one, but with `shell: true` it joins command and args UNQUOTED, so `process.execPath` at `C:\Program Files\nodejs\node.exe` splits at the space and cmd.exe runs `C:\Program` - which is why a real binary never gets a shell and `scripts/gates.js` sets the flag it once lacked. And a timed-out job is killed with `taskkill /T` (`_toolKill`), because killing the shell child alone leaves the installer running. The Claude CLI is resolved per call by `_claudeCli()`: `where claude` picks the native `claude.exe` (no shell) over the npm `claude.cmd` shim (shell), so a native install no longer reads as "not installed". `.mcp.json` starts both servers through `node scripts/mcp-launch.js`, the one launcher that works on both systems - Claude Code spawns MCP servers through Node, so a bare `npx`/`gitnexus` `.cmd` shim needs `cmd /c` on Windows, and `cmd` does not exist on macOS. Chromium detection is shared with the bootstrapper through `scripts/_playwright-paths.js`, so the tab and `npm run setup` can never disagree. A card that is not green shows the remedy for the REASON it is not green, never for its colour: Bitwarden missing offers an install and Bitwarden unauthenticated offers `bw login`, while a locked vault gets NO remedy here - the top bar owns unlocking everywhere, so the card only says the vault is closed. The probe asks `bw status` with the BW_SESSION this process holds, so the tab and `/api/bitwarden/status` can never disagree about the lock. Every remedy shows its command, copyable; a remedy the cockpit can run itself also gets a button. `POST /api/tools/run {job}` runs one of six jobs from a CLOSED table in `server.js` (`gitnexus-reindex`, `gitnexus-install`, `bitwarden-install`, `claude-install`, `playwright-setup`, `deps-install`) - the request names a job, never a command, and nothing from it reaches an argument, so adding a job is a deliberate edit under review. Node, npm and git carry a command and NO button on purpose: they are the runtime this server runs on. Installers use the npm distribution of each tool so one command works on macOS, Windows and Linux; the gitnexus pin and the analyze environment come from `scripts/_gitnexus-analyze.js`, shared with `scripts/bootstrap-gitnexus.js` - the two `GITNEXUS_*` values there are the difference between an index and a green card over an empty graph. The endpoint answers 202 rather than 200 (accepted, not done), serializes the start decision behind a chain lock so two clicks cannot spawn two installers, and refuses to spawn at all under `IS_TEST_MODE`. Progress is `job` at the top level of `GET /api/tools/status`, served fresh even from the cache so the tab polls it for one cheap request instead of twelve child processes. Covered by `tests/test_tools_status.mjs` and `tests/test_api_tools_status.js`.
