# App update: dirt exemptions, stash, adopt, fetch

Detail moved out of `CLAUDE.md` (sections "Agent model preferences", "Architecture") so the file Claude Code loads on every turn stays under its size limit. `CLAUDE.md` keeps the rules; this file keeps the reasoning, the incidents and the measurements behind them. Add new detail HERE and at most one line to `CLAUDE.md`.

Settings > Agents writes the chosen model into the `model:` frontmatter line of `.claude/agents/*.md`. Those files are committed, so the `.husky/pre-commit` hook runs `node scripts/restore-agent-models-for-commit.js`, which rewrites the STAGED blob back to the canonical model from `.claude/default-models.json` while leaving the working tree and every other staged edit in the same file untouched. One person's preference therefore never reaches the team through a `git add -A`. To change a default for everyone, edit `.claude/default-models.json` and commit that. Covered by `tests/test_agent_model_guard.mjs`. The commit hook is only half of it: those patched lines also make `git status` permanently dirty, and both app-update guards (`handleAppUpdate` and `_autoUpdateAppOnStartup`) refuse over a dirty tree, so on any machine where somebody picked a model the update was blocked forever by changes nobody typed. `_appUpdateDirtEntries` splits the porcelain output and exempts EXACTLY the agent files whose only diff from HEAD is the `model:` line (`_isModelOnlyAgentDiff`, pure and unit-tested) - an edited brief still blocks, with or without a model change, and every ambiguous case (no frontmatter, no model line, an unreadable blob, an added/deleted/untracked agent file, a path git had to quote) falls through to blocking, because the permissive direction here hard-resets somebody's work. The second generated line is the GitNexus banner in `AGENTS.md` and `CLAUDE.md` - `gitnexus analyze` rewrites its symbol counts on every run, so reindexing after a pull dirtied two files nobody edited; `_isGitnexusBannerOnlyDiff` exempts exactly that BLOCK under the same rule - the marked region between `<!-- gitnexus:start -->` and `<!-- gitnexus:end -->`, split out by the pure `_splitGitnexusBlock`, with the text before the start and after the end required to be byte-identical in both versions. It used to exempt the single counts LINE, which was right until a newer CLI rewrote the whole block and the exemption stopped matching the thing it was written for; every ambiguity in the markers (no end, a duplicate start, an end before its start) falls through to blocking, same direction as everywhere else in this helper. Those predicates sit in the one table `_APP_UPDATE_DIRT_EXEMPTIONS` that `_appUpdateDirtEntries` walks. Nothing is stashed and re-applied: the preference lives in the gitignored `data/agent-model-preferences/<slug>.json`, so `_applyAgentModelPreferences()` re-patches the files on the next boot. Both guards read the one helper, because they diverged once already. The tab itself is a card grid built from `GET /api/agents/list`; `GET /api/agents/read?name=` returns one brief, rendered in the shared document modal (`js/doc-modal.js` plus `js/md-render.js`). The name is matched against the roster, never joined into a path.

The same table carries a THIRD row that means something different, and the difference is written down here because the next person to add one will copy the wrong pattern otherwise. The two predicates above VERIFY that a diff has the shape a generator produces. The row for `^\.claude/skills/gitnexus/` verifies nothing (`onlyDiff: null`): it says the committed copy of those files - seven today, and the pattern is a directory PREFIX, so it covers whatever the CLI adds under that directory later, not only today's list - is the reviewed one and whatever is on disk may be discarded, because hand-editing `.claude/skills/gitnexus/*/SKILL.md` is not a workflow this repo has. Nothing is restored before the update either - the `reset --hard FETCH_HEAD` two steps later does exactly that, and one fewer write outside `.git` before the point of no return is the safer arrangement. Untracked entries got the same treatment for a CLOSED list of two literal prefixes (`_APP_UPDATE_UNTRACKED_GENERATED_PREFIXES`: `.claude/skills/gitnexus-` and `.claude/skills/generated/`), which is safe for the reason the 2026-09-04 comment already states - a hard reset leaves untracked files alone - and which unpicks a chicken and egg: the `.gitignore` entries that hide those directories can only ARRIVE in the update their presence was blocking. That is also the list's expiry date: once that `.gitignore` is on a machine an ignored path never reaches the porcelain and the list matches nothing, so it exists only for machines still on an older commit and is to be removed when no machine predates that update. Porcelain reports such a directory as one `?? path/` line, prefix matching covers that and the per-file form, and a path git had to quote never matches a prefix and therefore blocks, which is the direction we want. All of this exists because a starter zip plus the old unpinned CLI handed a new person nine modified tracked files they never typed, and the `core-scope` gate above means they could not commit their way out either.

What the exemptions cannot recognise gets a door rather than a hole. `POST /api/app/update` answers `dirty-tree` with `stashable` (every blocking path the stash can name), `unstashable` (a blocking path git had to QUOTE in the porcelain - a space, a quote, a control character - which a pathspec cannot name; `_appUpdateStashSplit`, pure) and `canStash`, and a re-submit carrying `stashDirty: true` runs `git stash push -u -m "cockpit-update <ISO> v<semver>" -- <every stashable path>` inside the existing `_appUpdateLockChain` - the same two-step, human-confirms-the-list shape as `confirmDeletes` in `POST /api/modules/publish`, and since 2026-09-12 every surface asks a `window.confirm` (`stashConfirmText`, one text for all four) before the second step. `-u` with an EXPLICIT pathspec, never bare, never `-a`. `-u` because on any machine where somebody builds a module every new file is untracked, and a stash that refused untracked entries hid its own button from exactly the people it was written for (seventeen `??` lines of real work, no button). Never `-a`: it would park `.env`, `.encryption-key`, `data/` and `modules/` in a git object, which is worse than the problem - and `-u` alone never touches an IGNORED path (measured). The pathspec is what makes even that belt unnecessary: the stash takes the blocking list and nothing else, so an exempt `model:` line stays in the tree for the reset to drop, same as before. `_stashShowFiles` reads an entry with `--include-untracked` (git 2.32+, tracked-only fallback), because a bare `stash show` lists only the tracked half and an entry made of nothing but new files read as empty. The load-bearing part is not the stash, it is what follows it - `git stash push` exits 0 having saved NOTHING when there was nothing to save (measured), so `_appUpdateStashDirty` re-runs the porcelain classification and checks its own message is on `git stash list -1`, and anything still blocking returns `dirty-tree` with NO reset. The app never pops: after the reset the stash's base is no longer HEAD, so it is an artefact you recover through the top bar's "Stash" pill (below) or by hand. `mapAppUpdateError` keeps returning a string; the button itself is rendered by each surface from the shared `dirtyTreeCalloutHtml` (Settings, the wizard, the modal) or built inline next to the message (the banner strip, which has no room for a file list and puts it in the confirm instead). `_autoUpdateAppOnStartup` reads the same helper, but in `unattended` mode (`_appUpdateDirtEntries(porcelain, ROOT, { unattended: true })`): it ends in a hard reset with nobody at the keyboard, so every row of `_APP_UPDATE_DIRT_EXEMPTIONS` carries an `unattended` flag and only rows marked `true` count there - the `model:` line (narrow, verified, re-patched from `data/agent-model-preferences/` on the next boot, so losing it costs nothing) plus the untracked prefixes, which need no flag because a hard reset never touches an untracked file. The GitNexus fence is `false`: the markers span the whole "GitNexus - Code Intelligence" chapter of `AGENTS.md` and `CLAUDE.md` (~46 lines of Always Do, Never Do and two tables that people really edit) and the predicate proves only that the edit sits inside it. The `^\.claude/skills/gitnexus/` row is `false` because it verifies nothing. Both stay honoured on the manual path, where a person sees the list and can say no. What the startup refuses that the click would exempt comes back as `attendedOnly` (always a subset of `blocking`, so the decision still reads `blocking` alone and nothing from `untracked` reaches it) and is written to the log in one `console.warn` naming the paths, because silence is what makes that direction dangerous. The body of `POST /api/app/update` goes through the pure `_appUpdateParseBody` (raw text in, `{ stashDirty }` out, nothing throws): only the literal boolean `true` opts in, and no body, `{}`, `null`, `[]`, garbage or the string `"true"` behave exactly as before the field existed. Covered by `tests/test_server_helpers.mjs` and `tests/test_app_update_stash.mjs`; there is no API test on `/api/app/update` and there cannot be, because its `reset --hard` runs BEFORE the `IS_TEST_MODE` gate and would eat the developer's working tree.

Parking the work was only half the escape hatch; getting it back was a git command in a terminal and a note in one browser's `localStorage`. `GET|POST /api/app/stash*` is the other half, and the top bar's "Stash" pill (`js/topbar.js`, `js/stash-modal.js`, decisions and copy in the pure `js/stash-helpers.mjs`) is where a person reaches it: the entry list, the files one entry carries, apply, and drop. Three things about it are load-bearing. An entry is addressed by its **commit SHA**, never by `stash@{N}`: the index shifts under every drop and two entries can carry the same subject, so the ref the browser read a minute ago may name somebody else's work by the time a button is clicked - `_stashResolve` re-lists and finds the sha every time, and `git stash drop` needs a ref (`apply` takes a sha, `drop` answers "is not a stash reference", measured), which is exactly why that resolution step exists rather than being skipped for `apply`. The app runs `git stash apply` and NEVER `pop`, the same rule `_appUpdateStashDirty` follows one step earlier and for the stronger reason: after the update's hard reset the entry's base is a commit that is gone, so a conflict is the EXPECTED outcome and losing the entry to it would be unrecoverable. So a conflict is not reported as a failure - the work IS in the tree with markers in it, and `stashApplyOutcome` says so, says the entry survived, and says the markers will block the next update too; the entry is removed only by a separate, confirmed click. And the success answer lists the files THAT ENTRY carried (`git stash show --name-only`), never `git status --porcelain`, which after a successful apply reports the whole dirty tree - one stashed file read as forty-one, measured. The two writes run inside `_appUpdateLockChain`, so an apply can never interleave with an update's reset, and both refuse under `IS_TEST_MODE` because they operate on ROOT, which in the API suite is the developer's own tree; `tests/test_api_app_stash.js` asserts that refusal and the read-only routes, while the git behaviour itself - apply, the conflict, drop, and the sha-outlives-the-ref property - is driven against real throwaway repositories with `root` injected in `tests/test_stash_api_helpers.mjs`, the same shape `_appUpdateStashDirty` is tested in. The modal leads with the hand-off rather than the button, because that is the route that actually works on a conflicted entry: `claudePromptForStash` builds the English instruction a person copies and pastes to Claude, naming the sha (not the ref) and saying apply-not-pop. The pill is the ONE top-bar slot that ships no skeleton and no markup of its own beyond an empty div - it is absent unless `git stash list` has something, so reserving width for it would flash a grey bar on every load for everybody. And the dirty-tree answer now carries the "stash and update" button in the update MODAL as well (`js/update-modal.js`, the same shared `dirtyTreeCalloutHtml`), which is where most people meet an update - answering there with a sentence pointing at Settings > System was why nobody found the button. `#update-modal-versions` had to become a `<div>` for that: the parser breaks a `<div>` out of a `<p>`, which would have dropped the button outside the modal body. The sticky banner (`js/update-banner.js`) carries it too since the same day - the strip has no room for a file list, so its confirm dialog carries the list, and the destructive step stays one deliberate "yes" away. Covered by `tests/test_stash_helpers.mjs`, `tests/test_stash_api_helpers.mjs` and `tests/test_api_app_stash.js`.

The cockpit core is not where the team's work lands: people build and ship MODULES under `modules/`, and the core stays a stable, updatable base. There is no in-app branch switcher and no separate developer mode — a work branch is created by hand with `git checkout -b <name>`. The starter package is the zip GitLab builds with `git archive` - every tracked file and NO `.git` - and `npm install` cannot repair that, because the fetch needs the project token and the token lives in Bitwarden. So the server ADOPTS the archive the first time a request holds a token and finds no repository (`scripts/_app-repo-adopt.js`, called from both `handleAppCheckUpdate` and `handleAppUpdate` through `_ensureAppRepo`, serialized on its own chain): `git init`, `origin` at `APP_REPO_URL_DEFAULT`, one fetch of `main` with the token, then `update-ref` plus `read-tree` so `main` and the INDEX point at the commit the archive was cut from - never a checkout of the tree, never a reset. Which commit that is comes from `SOURCE_COMMIT`: its committed content is the literal `$Format:%H$` and `.gitattributes` marks it `export-subst`, so `git archive` (and therefore GitLab's download button) stamps the hash in while a clone keeps the literal, which reads as "no hint". Without a usable hint the last thirty commits of `main` are tried newest-first with `read-tree` plus `git diff --quiet` (modes and CR at end of line ignored, because a zip tool may drop the executable bit and a Windows editor may add a CR; `SOURCE_COMMIT` itself excluded, because a stamped hint for a commit `main` does not have differs from every candidate by construction). The ONE write outside `.git` is putting `SOURCE_COMMIT` back to its committed blob once the hint is consumed - the stamped hash is not the committed content, so left alone it was the single modified file that blocked every update. Nothing matches, or the fetch fails -> the `.git` this call created is removed again and the handler answers `adopt-no-match` or the classified git error, so the next call starts from the same state; a `.git` that existed before is never removed and an unborn one (an interrupted attempt) is resumed. Adoption also persists `core.fileMode false`, and only on the repository it just created: the candidate scan already compares with `-c core.fileMode=false` because a zip tool may drop the executable bit, and without the setting that same lost bit came back as five permanently modified files the moment the scan was over. After adoption `git status` is clean and `HEAD` is exactly the tree the person runs, which is what lets the existing dirty-tree guard and the hard reset to `FETCH_HEAD` do their job unchanged; `check-update` also falls back to `HEAD` when no update was ever recorded, so a tree already at the remote's HEAD stops announcing an update it would apply as a no-op. `_appRepoUrl()` replaced the boot-time constant for the same reason: the origin can appear under a running server, and it is pinned to ROOT's own `.git` because `git -C` walks up and an archive unpacked inside somebody's repository would report THAT origin. `analyzeCliArgs` in `scripts/_gitnexus-analyze.js` adds `--skip-git` while there is no `.git`, so `npm run setup` on a fresh archive indexes the tree instead of dying on "Not inside a git repository". Covered by `tests/test_app_repo_adopt.mjs`. Whatever fetches this repository names an explicit destination for `main` (`ORIGIN_MAIN_REFSPEC`), and that is not a style preference: `git fetch <url>` with no refspec writes FETCH_HEAD and NOTHING else - git does not match the URL against a configured remote - so `refs/remotes/origin/main` stayed wherever the clone or the adopt put it while the updater walked local `main` forward one release at a time. Thirteen releases later an editor was offering a person thirteen of the maintainer's own commits to push, behind a GitLab sign-in they had no business completing (2026-09-15). Both update paths therefore fetch through the one `_appUpdateFetchArgs` argv and the `app-fetch-refspec` rule in `scripts/check-conventions.js` warns on a new bare-URL fetch into ROOT; the token still rides as an argument and never reaches `remote.origin.url`, which is why the named remote is NOT the answer here. That fix cannot reach a machine already apart - `_shouldAutoUpdateOnStartup` returns early for every boot with a recorded state hash, so a machine at the newest release never fetches again - so `repairStaleOriginMain` fast-forwards the ref at boot with no network, and ONLY when HEAD equals the hash the updater recorded (proof the commit came from the remote, so a locally authored commit stays visible as outgoing) AND the ref is an ancestor of HEAD (so it is never rewound over an update this machine has not taken yet). Its neighbour `quietCredentialPrompts` clears `credential.helper` for this repository alone, because an HTTPS origin plus anything touching the remote in the background - VS Code's `git.autofetch`, which was `true` on the machine this was reported from - means Git Credential Manager pops a modal sign-in for an app they never commit to. Repository-local, so it can never be committed and never dirties the tree; a `.vscode/settings.json` would be the obvious lever and is the wrong one, because `.vscode/` is gitignored here and un-ignoring it hands a modified tracked file to everyone who keeps personal editor settings, blocking the very updates this repository exists to deliver. Both refuse rather than act on an SSH origin or a helper somebody configured locally. Covered by `tests/test_app_update_fetch.mjs`.
