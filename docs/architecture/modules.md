# Modules: loader, Modules tab, catalog, publish

Detail moved out of `CLAUDE.md` (section "Architecture") so the file Claude Code loads on every turn stays under its size limit. `CLAUDE.md` keeps the rules; this file keeps the reasoning, the incidents and the measurements behind them. Add new detail HERE and at most one line to `CLAUDE.md`.

Modules are plug & play directories under the gitignored `modules/`; the loader in `server.js` discovers them at startup, mounts routes under `/api/m/<id>/`, and `js/module-host.js` builds the sidebar and `VIEW_REGISTRY` entries from `GET /api/modules/manifest`. Module client assets are served under `/modules/<id>/client/`; a module's own BUILT app (e.g. a Vite `dist/`) is served from a second static root, `/modules-data/<id>/public/` -> `MODULES_DATA_DIR/<id>/public/`, so a build never lands inside the module's own git tree. That root exists to be FRAMED - a module can paint a real built app inside a phone frame - so it is the one prefix that answers `X-Frame-Options: SAMEORIGIN` (`frameOptionsFor`) and a CSP of its own (`cspFor`, `CSP_MODULES_DATA`): `script-src` gains `'unsafe-inline'` because a Vite `index.html` boots its theme from an inline script, while `connect-src 'self'` and `frame-src 'none'` are tighter than the cockpit's own policy, so a framed app reports nothing to an analytics host and frames nothing itself; both helpers read the same `FRAMEABLE_PATH_PREFIX` and are pinned in `tests/test_server_helpers.mjs`. The Settings > Modules tab (`js/settings-moduly.js`) lists installed modules straight off the disk through `GET /api/modules/installed`, toggles them on/off by writing `data/modules-registry.json`, deletes a module's directory, and exports/imports modules as zip archives built by the dependency-free `scripts/zip.js`. Both lists there - installed and Catalog - are TABLES over `.ds-table`, not card grids, because this list is meant to grow: five columns (`Module`, `Version`, `Status`, `Place in menu`, `Actions`), sorted by the name the row shows and GROUPED by the place a module takes in the menu (`js/module-menu-groups.mjs`: one tbody pair per group in rail order, then `Own menu item`, then `Outside the menu`; the group comes from `hubPageTarget`, the same predicate the sidebar uses; every group starts collapsed on each entry to the tab - `renderModulesSection({ fresh: true })` from `renderSettingsView` - a toggle is a real `ds-row-toggle` button with `aria-expanded`/`aria-controls`, and a search or area filter opens every group with a match and hides the empty ones; covered by `tests/test_module_menu_groups.mjs`). Above that table two to-do lists - "Needs publishing" (not in the catalog, or a local version above it) and "Needs updating" (the catalog is newer) - come from the pure `moduleAttention` (`js/module-attention.mjs`, versions through `classifyModuleUpdate`), each row with ONE action: `Publish` opens the usual publish modal, `Update` runs `installFromCatalog` (the Catalog's own install flow, exported from `js/settings-moduly-katalog.js`). A module whose publish MR is still open reads "Awaiting merge" with a link, from `GET /api/modules/pending-publishes` (open catalog MRs whose source branch is `modulesPublishBranchName`'s shape, `parsePendingModulePublishes`, always 200, 60 s cache keyed by the token, `force=1` after a publish from the tab); an unreadable catalog shows one line with "Check again" instead of guessing. A module whose files differ from the catalog copy at an EQUAL version (`GET /api/modules/publish-drift`: what `_collectModuleFiles` would send compared with the catalog tree's blob ids through `gitBlobSha` / `modulePublishDrift`, so no content is downloaded; always 200, 60 s cache, `force=1`) is on the publish list as "Changes without a new version" with a "Bump to X.Y.Z+1" button (`POST /api/modules/bump-version`, `bumpManifestPatch` edits only the version literal under `withModulesLock`); its "Publish" stays disabled until then, because the publish version gate would refuse it. The drift read never holds the lists back - they paint with the last known drift and repaint when it lands. "Refresh" next to "Upload from file" re-reads the disk and all three sources with `force=1`. Covered by `tests/test_module_attention.mjs`, the `parsePendingModulePublishes` block in `tests/test_server_helpers.mjs` and `tests/test_api_modules_catalog.js`, and everything else - description, author, origin, capabilities, tags, views, declarations and the local git repository - in one details modal. `js/module-card.mjs` still renders every block of it (the file kept its name), so `renderModuleDetailsBody` is the ONE body both modals open and an installed module cannot describe itself differently from its catalog entry. Two things are load-bearing there. The git block's buttons carry the same `data-moduly-git-*` attributes the card used, and the modal is mounted on `document.body` - outside the section the delegation sits on - so the details modal binds `_handleClick` itself, and the two git actions that re-render the whole section close it first. And the tooltip on an icon-only action is a `::after` on the button, which `.ds-table-wrap`'s `overflow: hidden` would clip: that is why a narrow viewport DROPS the `Miejsce w menu` column instead of scrolling the table sideways. The same tab's Catalog section reads a shared, curated catalog from a separate `cockpit-modules` repository through the GitLab REST API only (`GET /api/modules/catalog`, token `COCKPIT_MODULES_TOKEN`, never cloned, never written to), decides each row's `Zainstaluj` / `Update` / `Zainstalowany` through the pure `catalogRowState` in `js/module-updates.mjs` - the same `classifyModuleUpdate` the update banner uses, over the installed version read from `GET /api/modules/installed`. Two endpoints answer "what modules are there" and they mean different things: `/api/modules/manifest` is the `loadModules()` snapshot taken at BOOT (which is why every install answers `restartRequired`), `/api/modules/installed` is the fresh disk scan. A version comparison, a dirty check or a list of what is installed is a DISK question and belongs to the second; the first is for what is LOADED, and `js/module-host.js` is its one legitimate browser consumer. The Catalog used to compare against the snapshot with a comparator of its own, so a `module.json` bumped after the last restart (a publish, an edit) showed six up-to-date modules as `Update` - an update whose only outcome was the 409 `module-dirty` guard, because a publish never commits the module's local repository. `manifest-boot-snapshot` in `scripts/check-conventions.js` warns on any other browser file reaching for the snapshot, and `tests/test_module_updates.mjs` pins the state function and the source. `POST /api/modules/install` downloads a chosen module into `modules/<id>/` through a dotfile temp directory once its manifest validates.

Every `modules/<id>/` is its own git repository WITHOUT a remote (`scripts/_module-git.js`, created by the scaffold, the catalog install and the zip import, or by "Initialise repository" on the module `ds-card`): nothing in it synchronises with anyone, Settings > Modules shows its state from `GET /api/modules/installed`, overwrite and remove refuse with `module-dirty` while it has uncommitted changes, and the only way a module reaches the team is still `POST /api/modules/publish`. The publish modal's status (stable / beta / deprecated) is SAVED, not merely sent: it used to reach only the catalog's curation entry on the GitLab branch, so the installed card could never show it and the modal reopened on "beta" every time. `status` is now an optional `module.json` field (validated against the one list `MODULE_STATUSES`, which `MODULES_CATALOG_STATUSES` and `MODULES_PUBLISH_STATUSES` derive from), the handler writes an explicit, valid `body.status` back into the manifest through the pure `setManifestStatus` BEFORE collecting files (so the published copy carries it too, and an unreachable GitLab does not lose it), the modal preselects it, and `renderMaturityBadge` in `js/module-card.mjs` is the ONE renderer both cards use - a missing status draws no badge rather than guessing "stabilny". Covered by `tests/test_modules_publish.mjs`, `tests/test_module_card.mjs`, `tests/test_module_loader.mjs` and `tests/test_api_modules_catalog.js`. The catalog entries published before `area` existed are backfilled by `POST /api/modules/catalog/migrate-areas` (curl only, like `admin/reset`; `dryRun: true` answers the plan and writes nothing): `POST /api/modules/publish` cannot carry that fix, because its version gate refuses an equal version and bumping five versions to add one field would rewrite five whole file trees, so this is the publish flow minus the module files - one branch `katalog/obszary-<stamp>`, one commit whose actions are `catalog.json` (`setCatalogEntryAreas`, pure, never adds an entry - an uncurated module takes its status from its manifest and a curation entry created here would silently turn that into `stable`) plus each `modules/<id>/module.json` (`setManifestArea`), one merge request. The area comes from `areas` in the body first and from the installed module of the same id second (`planCatalogAreaBackfill`, pure), never from a default; an entry with no source is reported as `skipped`, and the catalog is re-read fresh rather than from the 60 s cache because the plan must be made against today's remote. Driven end to end against the in-process GitLab stub in `tests/test_api_modules_catalog.js`, which records the branch, commit and MR writes. Publishing over an existing catalog copy can now delete: `buildPublishActions` emits a `delete` action for every path GitLab has under `modules/<id>/` that the files being sent no longer carry, computed against the full tree read by `_modulesCatalogTreeAll` (never a partial one - an incomplete page refuses the whole publish rather than silently dropping the deletions). The pure `publishDeleteGuard` decides whether those deletions may proceed: none is always fine, not one existing path being re-sent (not even `module.json`) is `409 publish-tree-mismatch` with no override (the read tree does not look like the module this caller holds), more than half the catalog copy going is `409 publish-destructive`, overridable only by an explicit `confirmDeletes: true` re-submit - the modal shows the file list and an "Publish anyway" button for that one. Each install, zip import and successful publish records its origin - source, version, timestamp - in the gitignored `data/modules-origin.json` (`MODULES_ORIGIN_FILE`, mirrors `data/modules-registry.json`'s tmp+rename discipline), surfaced per module as `origin` on `GET /api/modules/installed` and read off the card ("Z katalogu: 0.1.0, 05.09.2026"). `publishBaseWarning` (`js/module-updates.mjs`, next to `publishVersionGate`) compares that recorded base against the catalog's current version and warns, never blocks, when the base is strictly older - the gap the version gate alone cannot see: a bumped version does not prove the tree still contains what everyone else published in between. `upsertCatalogEntry` stamps `owner: { slug, name }` on a catalog entry's first `add` from `_localIdentity()` and never lets a later `replace` overwrite it; `publishTakeover` compares the publishing identity against that stored owner and, on a mismatch, adds a `[Takeover]` marker to the MR title and a warning both in the MR description and in the publish modal. All three signals - the delete guard's refusal, the base warning and the takeover warning - are informational or overridable, never a hard block: the human reviewing the merge request has the last word, same as every other publish. That reviewer is who the "MR:" chips in the top bar exist for: `GET /api/merge-requests/counts` (a `repos[]` shape plus `shortLabel`, one row `modules` today - the chip reads `KM`, its tooltip spells the catalog out) asks the catalog project for `merge_requests?state=opened&per_page=1` through the same `_modulesCatalogGet` and reads the count off `x-total` (`parseOpenMergeRequestCount`, pure), so the wire carries no MR body; it is always 200 (`error: 'no_token'` on a fresh install, `gitlab_error` when GitLab does not answer, the chip reads "-"), cached 60 s and keyed by the TOKEN like every GitLab cache here, so `refreshTopbarAfterSecrets` repaints it with no bypass parameter after an unlock. `js/topbar-mr-helpers.mjs` decides which rows paint (a `no_token` row is dropped, the slot stays empty) and what a chip says; the client renders `shortLabel`, `label` and `webUrl` from the payload and keeps no repo list of its own, so the app repository becomes a second chip with one server-side line. Covered by `tests/test_topbar_mr_helpers.mjs`, the `parseOpenMergeRequestCount` block in `tests/test_server_helpers.mjs` and the `merge-requests/counts` block in `tests/test_api_modules_catalog.js`, driven against the stub GitLab's `merge_requests` arm.

A module names the team data it touches in its own `module.json`, `dataRepos[]`: `access: 'write'` (default) means it owns the paths and sends them from its own sync row, `access: 'read'` (non-empty `paths` required, `validateModuleManifest`) makes the entry a VIEW - the reader's row counts and dates those files and the module gets its status bar, but ownership and the push stay with the writer. A module may declare one repo twice (write plus read); rows merge per module id and carry `access: 'write' | 'read' | 'mixed'`. The core keeps NO per-module scope: `SYNC_CORE_SCOPES` lists only what the core itself writes (`_academy`, `_team`, `_prototypes`), and `js/module-sync-bar.js` has no override map - the row id is the module id. `scripts/new-module.js --data "<repo>[:<paths>][:read];..."` writes the declaration at creation, and `check-conventions --modules` warns on `module-data-undeclared` / `module-data-repo-unknown`. Covered by `tests/test_module_loader.mjs`, `tests/test_new_module.mjs`, `tests/test_check_conventions.mjs`, `tests/test_server_helpers.mjs`, `tests/test_api_sync_modules.js`.

The same declaration is what `ctx.dataRepoDir(name)` answers from (`_moduleDataRepoDir` in `server.js`): the plaintext directory of a repo the module declares in `dataRepos[]` (write or read entry, route id or remote name), `null` for anything undeclared or unknown, and never created (for an `access: 'read'` entry the directory is read-only by contract, and ctx carries no repo lock, so a write there can race `clear-plaintext`) - a missing directory means the source is not cloned and a write must be refused, because a plaintext tree made before the clone is how team data was lost on 2026-09-05. It exists so a module stops re-deriving `data-sub-repositories/ds-<id>`. A module that may land on an older core keeps a fallback (`DATA_SUB_REPOS_DIR`, then the default layout).

## Widgety pulpitu

The dashboard (`#view-dashboard`) can show tiles from installed modules. A module declares `widgets[]` in `module.json` (`validateModuleWidgets` inside `validateModuleManifest`: id, label, `client` = relative `client/….js` path without `..`, `variants[]` of `cols` 2/3/6 and `rows` 1/2, `defaultVariant`; at most 6 widgets and 6 variants; an absent field adds no error, which is what keeps every installed module valid). `moduleWidgets(manifest)` returns the catalog entry; a module without `widgets[]` gets one built-in shortcut widget (`shortcut`, 2x1, `builtin: true`) so the picker is always full.

The per-machine layout lives in gitignored `data/dashboard-layout.json` (env override `DASHBOARD_LAYOUT_FILE`), behind `GET|PUT /api/dashboard/layout`. Both validate against `_loadedModules`, the BOOT snapshot, not against a fresh disk scan: that is what the browser can really mount, so a module installed or re-enabled after boot appears after the next restart, exactly like its rail item. `GET` answers `{ hasModules, layout, available }`; `available` is the catalog, so the browser never reads `/api/modules/manifest` (rule R14). `GET` filters stale items through `normalizeDashboardLayout` but never rewrites the file, so re-enabling a module brings its tile back. `PUT` is strict (`400 invalid-layout` with the `index` of the first bad item, nothing written), `checkOrigin` (415 without JSON), `withDashboardLayoutLock`, tmp+rename.

Scaffold presets (`WIDGET_VARIANT_PRESETS` in `scripts/new-module.js`): `s` 2x1, `s2` 2x2, `m` 3x1, `m2` 3x2, `l` 6x1, `xl` 6x2; the validator accepts any `cols` in 2/3/6 with any `rows` in 1/2, so every width has a `.dash-widget--rows-2` twin.

`ctx.kit` (js/dashboard-widget-kit.js, frontend slice) hands widgets block builders (tiles, donut, big, segments, progress, bars, spark, heatmap, people, avatars, timeline, pill, `blocks(list, {cols, rows})`, `hydrateAvatars`); avatars resolve through the team directory (`js/team-directory.js`: team photo > GitLab avatar > initials). The scaffolded `client/widget.js` paints through `ctx.kit` when present.

Client side (frontend slice): the core draws the frame, the module paints the body through `renderWidget(el, ctx)`; a failure stays in its frame. Exactly one `ds-btn--primary` exists on the dashboard in every state. Tests: `tests/test_module_loader.mjs`, `tests/test_dashboard_layout.mjs`, `tests/test_api_dashboard_layout.js`, `tests/test_new_module.mjs` (`--widgets`).

## Catalog source: local folder (default) or GitLab (opt-in)

The module catalog lives "under one roof": `catalog/catalog.json` plus `catalog/modules/<id>/` in this repository is the DEFAULT source (`MODULES_CATALOG_DIR` moves it). Setting `MODULES_CATALOG_REPO_URL` switches to a shared GitLab catalog read through the REST API, as before. `modulesCatalogMode()` decides per request, so an `.env` reload applies at once.

The two sources share one code path. Every catalog read builds a GitLab REST URL (`_modulesCatalogFileRawUrl`, `_modulesCatalogTreeUrl`, `_modulesCatalogCommitsUrl`, the project probe, the branch head) and hands it to `_modulesCatalogGet` / `_modulesCatalogGetBinary`; in local mode those answer the same URL from the folder through `localCatalogRead`, in the same `{ok, status, text, headers}` shape. So `_modulesCatalogRefresh`, `_modulesCatalogTreeAll`, install, the drift scan and the reconcile run unchanged, and `parseModulesCatalog` / `mergeModulesCatalog` / `upsertCatalogEntry` are reused as they are. Local specifics: one revision (`ref` ignored, one pseudo-commit per path, no branch head - nothing is pinned), no merge requests (pending publishes answer an empty list, the `MC` chip row is left out), tree rows skip what a publish never sends (`_isModuleJunkEntry`) and carry git blob ids of the LF bytes, so drift detection works on disk. Publish in local mode (`_modulesPublishLocal`) runs every shared gate (area, manifest, version, status write-back, `publishDeleteGuard`) and then copies the files into `catalog/modules/<id>/` (`_localCatalogWriteModule`: tmp+rename per file, deletes pruned, dotfiles left alone) and upserts `catalog.json` - no branch, no MR, no token; the person commits the change. `GET /api/modules/catalog` carries `catalogSource: { mode, location }`, which Settings > Modules > Catalog shows (`catalogSourceLine`). `npm test` runs `catalog/modules/<id>/tests` too (an installed copy of the same id wins), `npm run test:core` leaves them out, and `npm run lint:modules` covers `catalog/modules`. Covered by `tests/test_api_modules_catalog_local.js`, the local block in `tests/test_modules_publish.mjs`, `tests/test_unit_discovery.mjs` and `tests/test_catalog_source_line.mjs`; the GitLab source keeps `tests/test_api_modules_catalog.js`, whose servers set `MODULES_CATALOG_REPO_URL`.
