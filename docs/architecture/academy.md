# Academy

Detail moved out of `CLAUDE.md` (section "Academy") so the file Claude Code loads on every turn stays under its size limit. `CLAUDE.md` keeps the rules; this file keeps the reasoning, the incidents and the measurements behind them. Add new detail HERE and at most one line to `CLAUDE.md`.

Settings is not the only view the core owns: `#view-academy` (`js/academy.js`, reached from the dashboard card "Academy") is the training path that walks a new person from an empty VS Code to a published module of their own. It is a CORE VIEW, not a module - `academy` is on `RESERVED_MODULE_IDS` - and deliberately gets NO `HUB_FLYOUT` entry, because a key there would make it a hub and `js/app.js` would redirect `#academy` to the dashboard. Which is why its rail item - "Academy", pinned right under "Start here" in the bottom group, because in the first days this is the view a person opens most and the dashboard card cost a detour every time - is STATIC markup in `index.html` rather than config, exactly as the onboarding wizard's is. Four stages plus a mural and a gallery tab: environment (VS Code terminal, Claude Code CLI, login, model choice, auto mode, the in-app terminal), terminal and CLI craft, "Build your own module" (scaffold with `scripts/new-module.js`, enable it in Settings > Modules, extend it with `/new-idea`, export it, publish it - the contract-test step is gone, because `/new-idea` writes the tests itself), and the non-gating community tips. Step 3 of the FIRST stage opens `docs/guides/repo-guide.md` in VS Code (key `przewodnik-po-repo` in `COCREATE_OPEN_FILE_MAP`, with a `tip` naming the Markdown preview shortcut) - the one human-facing digest of this file, `modules-template/README.md` and the agent and skill indexes, because on day one a person is not supposed to read the agent-facing files; when a rule here changes in a way a person must know, that guide is where it lands. The digest is a first-day shortcut and not a replacement: `step-3b` of the THIRD stage, sitting deliberately before "Grow your module", opens the whole of `CLAUDE.md` and `README.md` (keys `claude-md` and `readme`) once the person has a working module to change, which is the first moment those files pay for themselves. The first step of the third stage opens `docs/guides/module-anatomy.md` in the shared document modal (`guideDoc` on the step, a SLUG the client resolves to `/docs/guides/<slug>.md` and serveStatic answers) rather than dropping two source files into VS Code: a person needs the idea of a module before its manifest fields. Three later steps carry `openTab` - a hash route of this same app opened in a NEW browser tab - so "go to Settings > Modules" no longer costs the place in the course. Removing a step NEVER renumbers the ones after it: progress is keyed on the step id in each person's file, so `step-5` is simply absent and `step-6`/`step-7` keep their ids. Stage N unlocks only once THIS person finished stage N-1.

`js/academy-stages.mjs` is the single source of truth for the stage and step lists: the view imports it statically and `server.js` loads it lazily through `await import(pathToFileURL(...))`, so the two sides cannot drift apart. Progress lives in the team data repo as ONE FILE PER PERSON - `data-sub-repositories/ds-data/academy/progress/<person_slug>.json`, the plaintext working tree the sync encrypts on push, same pattern as `modules/demo-hub` - keyed on the `person_slug` from `GET /api/whoami`, and there is no second identity resolver. Nobody ever writes anybody else's file, which is what makes the autopublish safe: every verified step immediately encrypts and pushes THAT ONE file, so the Settings sync panel is not part of the training loop at all. Two invariants hold it up. The pre-push pull is UNCONDITIONAL, not "only when we are behind": a targeted push that merged remote commits into the mirror without decrypting them would leave the mirror holding `.enc` files absent from the plaintext tree, and the next FULL push runs `encryptTree`, which builds `keepEnc` from plaintext and unlinks every `.enc` it does not find - deleting every teammate's progress. And both `withDataTierLock` and the repo file lock are held across the encrypt AND the git calls, so this can never interleave with `dataTier0Encrypt()`'s whole-tree walk. Staging names the single `.enc` path explicitly; `git add -A` would sweep in whatever else the pull left dirty. A publish that cannot happen is never an error and never fails a step: `IS_TEST_MODE`, a missing write token, a missing encryption key (pushing plaintext instead is the one thing this layer exists to prevent), a locked repo or an unreachable remote each come back as a `sync` state that the step's callout explains in plain words, with the progress already safe on disk. The last outcome is cached in the gitignored `data/academy-sync.json` rather than in the pushed file, because writing the result into the file it describes would re-dirty it and leave the mirror permanently one commit behind. A fresh clone with no `ds-data` is a normal state, not a failure: reads answer 200 with an empty shape and `storage: 'unavailable'`, writes answer 409 pointing at the sync panel. Eight endpoints under `/api/cocreate/*` (the API prefix predates the view's name): `progress`, `unlock`, `verify-step`, `modules` (the gallery), `mural` (GET and POST), `open-file` and `admin/reset`. A step is verified either on the person's word (`self-attest`) or by the server - and every server check that concerns a module matches the id against the on-disk module list and then works from the MATCHED record's path, never from the request string; the section now spawns NO child process of its own. It had exactly one, `claude auth status` behind the Claude Code login step, and that is the cautionary tale for every future server check: the command answers "are there credentials on this machine", not "is this CLI logged in", so it passed the step for a person the CLI still asked to log in. No cheap call answers the second question - a real API call costs money and seconds - so the step is `self-attest` and its instruction names `/login` and `claude auth login`, the commands the old FAILURE message never named (it said to re-run the diagnostic). A check that cannot answer the question the step asks is worse than no check, because a green tick stops a person from looking. `open-file` takes a KEY from a closed map, never a path. `admin/reset` is the ONE deliberate exception to "nobody writes anybody else's file": it takes a `person_slug` in the body and walks the same `_cocreateWritePerson` path as the person's own unlock and verify-step, so it is OFF unless `.env` carries `COCREATE_ADMIN_RESET=1` (403 `admin-disabled` otherwise), validates the slug with `_cocreateSlugSafe` before touching the disk, and is reached only with curl, never from the UI. The publish step passes on EITHER of two remote states, decided by the pure `cocreatePublishedState`: the `module/<id>-*` branch exists on the catalog remote (published, MR waiting - the catalog's `main` is protected, so the entry appears there only once a human merges), or the module is in `catalog.json` on `main` (merged - the MR is opened with `remove_source_branch`, so GitLab deletes the branch at that moment, and a branch-only check failed for good for exactly the people whose module had been merged). Every own module on disk is considered (`_cocreateOwnModules`), not the first by name, because a machine that installed a few catalog modules holds them next to the one the person built; `data/modules-origin.json` is deliberately not consulted - it is this machine's own claim and the step is about the remote. The Mural is the second thing that lives in that tree - `academy/mural/<person_slug>.md`, one markdown file per person with a server-owned YAML header - and it is the reason the publish helper takes a PATH (`_cocreatePushDataFile`) rather than a slug: a mural entry travels exactly the way a progress file does, with the same unconditional pre-push pull, the same two locks and the same single explicit pathspec. An earlier design kept the mural in the APPLICATION repository, so leaving a trace meant a branch, a commit and a merge request, and nobody saw the entry until a human merged it; here the file is team data, so a save is visible to everyone as soon as it syncs. It is written only for the caller's own `person_slug`, never for a name in the body, an empty body removes it, and the last step of etap-1 is verified by checking that THIS person has one. Every face in the view - the hero, the stage finishers, the tip authors, the gallery and the mural tiles - resolves its photo in one order through `js/team-directory.js`: the team photo from ds-data, then the GitLab avatar, then initials. A mural TILE shows the ANSWERS, not the questions: `js/academy-mural.mjs` (DOM-free, so the unit suite reads it directly) splits the entry on its markdown headings and hands the tile one block per section that actually has content - the heading as small print, the lines under it as the text. The first version flattened the whole entry into one 150-character excerpt, so the template's three questions ate the budget and no answer ever reached the card; a section holding only the untouched `- ` of the template is a blank form field and is skipped, while `None` is an answer somebody wrote and stays. Two blocks per tile, each clamped, so a grid of tiles stays even. Covered by `tests/test_academy.mjs` and `tests/test_api_cocreate.js`.
