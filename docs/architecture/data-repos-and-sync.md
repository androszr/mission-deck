# Data repos, encryption and sync

Vanilla-JS SPA (ES modules, no bundler) + a single-file Node.js HTTP server (`server.js`, no framework, no dependencies beyond `ws` + `node-pty`). There is no database: application JSON lives in the gitignored `data/` cache and team data lives in a registry of cloned data repos (`DATA_REPOS` in `server.js`), reached through `/api/data/<repoId>/<op>`; the registry holds ONE row by default - `data-tier-0` (`data-sub-repositories/ds-data/`, label "Team data") - and `DATA_REPO_DEFS` is the documented place to declare more (each then lives in `data-sub-repositories/ds-<id>/`, with its own `urlEnvVar`, `tokenEnvVar`, vault item, frozen `hkdfInfo` and `mirrorFormat`; a source whose key is born in this app also joins `OWN_LINE_ONLY_IDS` in `scripts/crypto-sync.js`, gets its key from `POST /api/settings/encryption-key/generate` and hands it to teammates through `/export`) — and the legacy `/api/data-tier-0/*` paths stay as a permanent alias for `data-tier-0`. All rows share one set of drivers (`_repoClone`/`_repoPull`/`_repoEncrypt`/`_repoDecrypt`, each taking the descriptor), so every source can be cloned and pulled. The dividing line for what a row may do is not read-vs-write, it is **does the operation call `encryptFn`**: `encryptTree` walks the PLAINTEXT tree and unlinks every `.enc` in the mirror it finds no plaintext source for, so running it against a source whose plaintext tree is empty or half-decrypted would wipe that mirror - and a push would publish the wipe. It now refuses with `encrypt-destructive` in two shapes, decided BEFORE anything is written: a plaintext tree that shares no file NAME with a non-empty mirror (`mirrorOverlap`, v1 names counted), which is the signature of a source cloned before its key existed, and a run that would drop more than 30% of a mirror over 50 files, the same numbers `decryptTree` uses. That case is real, not theoretical: the startup auto-clone fills the mirror the moment the vault opens, key or no key, and when the key arrived later the wizard ran `pull-stream`, whose pre-fetch encrypt unlinked every `.enc` in the mirror, `--autostash` carried the deletions across the merge and the next push would have deleted the team's data on the remote. `_repoPull` therefore falls back to `encryptFn(log, { prune: false })` when the guard fires (an ADDED local file is still work to carry, the removals are exactly what must not happen), the status row carries `decrypted` (true / false / null for cannot-tell, from `_repoDecryptedState`), and `POST /api/data/<repoId>/decrypt` (`generic: true` - it touches no git state and can destroy nothing the mirror holds) decrypts the mirror over the plaintext tree with `prune: false`, so a module's own downloads survive the first decrypt. The wizard's key step calls that op, never a pull, and `obwDataReady` is false while `decrypted === false`; the sync table shows `not decrypted` / `no key` with a `Decrypt` button in place of `up to date`. Covered by the guard block in `tests/test_crypto_sync.mjs` and, end to end against a real mirror and remote, by `tests/test_api_data_decrypt.js`. `data-tier-0` cannot reach that state because its plaintext directory IS the app's working tree; an additional source has nothing but a successful decrypt filling its own. So `generic: true` on `DATA_REPO_OPERATIONS` marks exactly the non-encrypting ops — `clone`, `pull`, their streams and `clear-dir`. `pull-overwrite`, the conflict and rebase repairs, and `local-changes` (which re-encrypts first, so `git status` on the mirror can see plaintext edits) stay `data-tier-0` only; `push` and `push-stream` carry `writable: true` instead, which `_repoServesOperation` opens for `data-tier-0` and for any additional row whose `pushEnabled` flag is `true` (see `DATA_REPO_DEFS`). `GET /api/sync-overview` publishes that split per row as `canPush` and `canListLocalChanges`, which is what the sync modal disables its buttons from — never a second list in the browser. Status `dirty` is `mirrorDirty || plaintextDirty`: `mirrorDirty` is the existing `git status --porcelain` check on the encrypted mirror, `plaintextDirty` comes from the read-only sonda `plaintextAheadOfMirror` (`scripts/crypto-sync.js`) over the plaintext directory the app actually writes to — the status handler never encrypts anything itself. Which installed module owns which pending file is computed the same read-only way: `GET /api/sync-modules` classifies the pending set from `dataRepos[].paths` of every enabled module, "Cockpit Core" is the complement, and `push-stream?module=<id>` (`_repoPushScoped`, data-tier-0 only) encrypts and stages that module's files one at a time and never through the whole-tree `encryptTree` — the same autopublish pattern as `_cocreatePushPersonFile` below. Its file list `GET /api/sync-modules/files` answers BOTH directions per row — `direction: 'send'` from `_repoPendingSet`, `direction: 'fetch'` from `_repoRemoteAheadPaths` grouped by the shared `_classifyRemoteAheadFiles` (which `_classifyRemoteAhead` is now a `.length` over, so the level-2 counter and the level-3 list it opens cannot disagree) — and `moduleHasFileList` opens that list whenever EITHER direction has something, because a row reading "0 / 2" used to have a dead badge and an empty list. A module row's two dates are the module's own, never the repository's: `remoteAt` is the newest `@{upstream}` commit that touched THAT module's files and `localAt` the newest pending mtime, else the newest `HEAD` commit that did - one `git log --format=%x01%cI --name-only <ref>` walk per ref (`_repoCommitDatesByPath`, 0.12 s on the deepest mirror) parsed by the pure `_newestCommitDateByPath` and bucketed by `_classifyCommitDatesByScope` through the same `nameMap` and `_matchScopeId` the counters use; a module no commit ever touched carries `null` on that line, deliberately not the repo date, because handing the repo-wide `_repoRemoteAt` to every row is exactly what made eight modules read the hour of whoever pushed last. The repo row keeps the repo-wide dates. There is no scoped PULL and there must not be one: git's unit is the commit, and decrypting one module's files alone leaves every other new `.enc` without a plaintext twin, which `plaintextAheadOfMirror` reports as a DELETION and the next `encryptTree` push would publish. So "Pull" on a module or a file row starts the SOURCE's pull (`data-act="pull"`, no `data-module`) and says so in its tooltip (`PULL_TIP`) — what the row picks is where the person looks, not what travels. Two things differ per source and are frozen because they are part of the key derivation or the wire format: the HKDF context string (`DATA_REPO_DEFS.hkdfInfo`; `DEFAULT_HKDF_INFO` applied to a source encrypted under another one yields a valid-looking key that fails every GCM auth tag) and the mirror layout (`DATA_REPO_DEFS.mirrorFormat`). `'v2'` (the default, and data-tier-0's) names each mirror file by an HMAC of its path; the legacy `'v1'` layout keeps the real name with `.enc` appended and salts a bare base64 body from the PLAINTEXT path. `decryptTree` dispatches per FILE on the `v2:` prefix (a migrating source holds both at once); `encryptTree` and `plaintextAheadOfMirror` take the format as an option, and `_repoEncrypt`/`_repoPushScoped` read `d.mirrorFormat` to pick `encryptBufferV1` or `encryptBuffer`. A source another tool still writes in v1 must stay v1, or a v2 push from here would fight it over the whole tree. `pushEnabled` is the separate flag deciding whether a row may write AT ALL - `mirrorFormat` only decides WHICH layout it writes when it does; a row with the flag gets a real `push`/`push-stream` and a real chain lock (`lockFn`), the others keep the no-op lock because nothing writes their mirror outside a decrypt. A tier may also carry a `.syncignore` at its plaintext root (gitignore subset, itself encrypted and shared, `scripts/crypto-sync.js`): `encryptTree`, `mirrorOverlap`, `plaintextAheadOfMirror` and `decryptTree` all skip what it names, a full encrypt pass sweeps the stale `.enc` of a newly excluded path out of the mirror, `decryptTree` never writes such a blob nor deletes the receiver's local copy, and a policy that would drop more than 30% of a mirror over 50 files is refused as `encrypt-destructive` like any other mass removal. For a row with `pushEnabled: false`, `plaintextAheadOfMirror` still treats the `<relPath>.enc` name as legacy — present, unchanged, no byte compare — because that row can never push it from here; for a pushable v1 row that same name IS the primary layout, so the probe byte-compares it like any other pending file. The sync table's "Send · fetch" column renders `filesToSend`/`filesToFetch` from `_repoPendingFileCounts`, never `ahead`/`behind`: those count COMMITS, and a push here encrypts, commits and pushes in one operation, so `ahead` is 0 for every edit a person has actually made and only turns non-zero when a push committed and then failed. `filesToSend` UNIONS three sets of mirror `.enc` names — uncommitted in the mirror, changed by an unpushed local commit, and edited in the plaintext tree but not yet encrypted (`plaintextAheadOfMirror` with `collectPaths`, which is why the probe returns paths and not just counts) — so a file in more than one of them still counts once. `filesToFetch` reads the last known upstream ref (`@{upstream}`) and takes no network, and git moves that ref on `fetch`/`pull`/`push` and on NOTHING else - so the whole fetch direction of the table (`filesToFetch`, `behind`, `remoteAt`) showed the remote as of this machine's last sync and a teammate's push stayed invisible until somebody pulled. `check-update` was never the escape hatch an earlier version of this sentence promised: it asks `ls-remote`, which writes no ref, it is data-tier-0 only, and no client ever called it. `POST /api/sync-overview/refresh` is that refresh - `git fetch --prune` per source behind `allSettled`, a 45 s per-source budget (a status check, not a transfer), a 60 s per-source TTL (`remoteRefreshDue`) that `force: true` bypasses, and one result per row so the table can say WHY a source is unknown instead of showing a confident 0. It is `generic`-safe for every source because a fetch writes inside `.git` alone and no path it reaches calls `encryptFn`, and it answers the FULL sync-overview payload (`_syncOverviewPayload`) so the client needs no follow-up GET. It is deliberately NOT wired into `_repoStatusPayload`: the top bar polls that every 60 s for every row, so the pill stays as stale as before until the sync window is opened or the loop pulls. The sync modal calls it unforced on open and forced from the "Check server" button; `repoStateBadge` (`js/sync-center-helpers.js`, moved out of the modal so `tests/test_sync_center_helpers.mjs` can pin it) finally has a branch for that direction - it had none, so a source the team had pushed to painted a green `up to date`, and the both-directions row says `to send and fetch` rather than only the local half. Covered by `tests/test_api_sync_overview_refresh.js` and the two pure gates in `tests/test_server_helpers.mjs`. `ahead`/`behind` stay in the payload for the auto-sync loop and the push preflight. `DATA_SUB_REPOS_DIR` relocates the additional sources' directories the way `DATA_TIER_0_DIR` relocates the first's; without it an api test asserting "this source is not cloned" reads whatever the developer running it happens to have fetched. Installed modules live in the gitignored `modules/` directory. English UI - every string that renders to a person (HTML text, `placeholder`, `aria-label`, `title`, toasts, error and status messages, prose in `docs/`, `templates/` and `README.md`) is plain English. Source stays ASCII — identifiers, comments, log lines, file names, view ids, API paths, CSS class names, slugs and commit messages carry no diacritics, and neither does a string literal that is an id, a path, a key or a value compared rather than displayed. The same applies to every module under `modules/`.

The team data repo `data-tier-0` (remote `ds-data-tier-0`, URL defaulted in `server.js` so `.env` needs no entry) is cloned into `data-sub-repositories/ds-data/`, served statically with `no-cache`, and pulled/pushed by `/api/data-tier-0/*` - manually only: the background auto-sync loop (`_startAutoSyncLoop`, gated on `AUTO_SYNC_ENABLED`) is no longer armed at boot and the System tab no longer offers its toggle, because it covered only one source at a time; the machinery stays so it can come back for every source at once. Nothing readable leaves this machine: `data-sub-repositories/ds-data/` is PLAINTEXT and is never a git repository, while the clone is the encrypted mirror `data-sub-repositories/ds-data-encrypted/`, one opaque `<hmac>.enc` per file. Push encrypts first, pull decrypts after, and both go through `scripts/crypto-sync.js` (AES-256-GCM, per-file HKDF subkey, deterministic salt/IV so an unchanged tree produces no diff). Path names are encrypted too, because a photo file named after a person would publish the roster even with every byte encrypted. The key is the `ds-data=` line in the gitignored `.encryption-key`; without it `encryptionReady` is false and sync refuses rather than pushing plaintext. Point the static server at the mirror or git at the plaintext dir and the property is gone - that split is the whole guarantee. Covered by `tests/test_crypto_sync.mjs`.

**Read declarations in the per-module view.** `_syncModuleScopes` (pure half `_buildSyncScopes`) builds each row as `{ id, label, entries, reads, declaredPaths, access }` from `dataRepos[]`: a write entry fills `entries` (ownership, `_matchScopeId`, the push), a `dataRepos[].access: 'read'` entry fills `reads` and only ADDS a view - the four classifiers (`_classifySyncPending`, `_classifyMtimesByScope`, `_classifyCommitDatesByScope`, `_classifyRemoteAheadFiles`, `_classifyRemoteAhead`) take a trailing `opts.reads`, which `_syncModulesForRepo` and `handleSyncModuleFiles` pass (via `_matchReaderIds`) and `_repoPushScoped` never does. The sum invariant is therefore stated over OWNERSHIP: `sum(filesToSend of rows with write entries) + core === repo filesToSend`; a row with `access: 'read'` is a view of files another row (a module, a core scope or `_core`) owns, excluded from that sum, and a file item in `GET /api/sync-modules/files` carries `owner` (the row that sends it; `_all` is read ownership-only so nothing is listed twice). A pure-read scope cannot push: `push-stream?module=<id>` answers `read-only-scope` before the clone check (`_readOnlyScopeRefusal`). The core holds no per-module list - `SYNC_CORE_SCOPES` names only `_academy`, `_team`, `_prototypes` (with `vendor/`) and `_proto-analytics` (`proto-analytics/`); a module names its own data, read or write, in `module.json`. Covered by `tests/test_server_helpers.mjs`, `tests/test_api_sync_modules.js`.

## Autostash conflict

`_repoPull` runs `git pull --rebase --autostash` on the mirror after the pre-pull encrypt has turned local plaintext edits into mirror changes. When the stash re-apply conflicts with what the team pushed, git still exits **0**: it prints "Applying autostash resulted in conflicts", keeps the stash, applies its clean part and leaves the rest unmerged (`UU`). The old code saw exit 0 and decrypted that tree, and the next push re-encrypted and `git add -A`-ed it - in one incident that published old versions of 23 edited files on a shared source; the edits survived only in the mirror's stash.

`_repoAutostashConflict` is the one check for that state, and the unmerged index is its only record (no state file). It runs right after the pull (before decrypt - the plaintext is untouched), and at the start of every `_repoPull` and `_repoPush` while the state lasts: without the second guard the pre-pull encrypt or the push's `git add -A` would settle the conflict silently in favour of the local plaintext and overwrite the teammate's edit instead. `_repoPushScoped` and `_cocreatePushDataFile` pull first, so they inherit it. The refusal is `error: 'autostash-conflict'` with `paths` (mirror names) and `files` (plaintext names: v1 from the name, v2 decrypted from the HEAD blob with the row's `hkdfInfo`).

The way out is `POST /api/data/<repoId>/resolve-autostash { keep: 'mine' | 'team' }` (`writable: true`: it only ever has work on a source whose pull pre-encrypts), offered in the sync error modal as "Keep my versions" / "Take the team's versions". It checks out the conflicted paths from the autostash commit (`mine` - refused with `stash-missing` unless the newest stash entry's subject says `autostash`) or from `HEAD` (`team`), then decrypts the WHOLE tree, exactly as a clean pull would: a teammate's edit to a file nobody touched here is already in the mirror but not in the plaintext, and decrypting only the conflicted files would let the next push re-encrypt the stale plaintext over it. The stash is never dropped. Covered by `tests/test_repo_pull_autostash.mjs` (throwaway repos).

## Concurrent edits of one file: merge on plaintext, never on ciphertext

Every `.enc` is ONE base64 line, so git can never merge two edits of the same file - even hunks a hundred lines apart collide on the `--autostash` re-apply, and the autostash conflict above follows. Most of those collisions are not real conflicts: two people changed different parts of one text file. `_repoReconcileBeforePull` runs after the pre-pull encrypt and before `git pull`: it fetches, and for every file changed both locally and upstream since the merge base decrypts the three versions (`crypto_sync.decryptMirrorBlob`, v1 and v2) and runs `git merge-file`. When EVERY overlapping file merges cleanly, the local `.enc` blobs go back to HEAD, the pull runs without a conflict and `_repoPull` writes the merged text into the plaintext after the decrypt - it is then ordinary work waiting for the next push. All or nothing: one real conflict, binary, non-UTF-8 text (the git wrapper's string stdout would mangle cp1250 "cleanly"), merged `.json` that no longer parses, delete/modify or undecryptable blob, and the function touches nothing (`unresolved` names the files in the log) - the pull then conflicts on exactly those files and the person picks a side through `resolve-autostash`. A partial merge would break that choice: resolve decrypts the whole tree and would overwrite the merged plaintext of the files that were reset to HEAD. A mirror that already carries unmerged paths is `_repoAutostashConflict`'s state and is never merged on top of. The `autostash-unmerged-gate` rule in `scripts/check-conventions.js` blocks any new `--autostash` call without an unmerged check (`--diff-filter=U`, an `*unmerged*` helper or `_repoAutostashConflict`) after it. Covered by `tests/test_repo_pull_reconcile.mjs`, including two end-to-end `_repoPull` cases.
