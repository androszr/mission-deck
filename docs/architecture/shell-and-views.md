# Shell, views and server layout

Detail moved out of `CLAUDE.md` (section "Architecture") so the file Claude Code loads on every turn stays under its size limit. `CLAUDE.md` keeps the rules; this file keeps the reasoning, the incidents and the measurements behind them. Add new detail HERE and at most one line to `CLAUDE.md`.

`index.html` is the shell: `js/theme-boot.js` blocking, then `styles.css` and the three DS stylesheets, then `js/app.js` as a module. Navigation is hash-based — `#view-<id>` selects one `<div class="view-section" id="view-<id>">` and hides the rest. `js/view-registry.js` holds `VIEW_REGISTRY`, mapping each view id to a lazy `importFn` plus its `render`/`runInit` hooks, so a view's module is only fetched when first opened. `js/core-hubs.mjs` declares the eight rail hubs and `js/sidebar-flyout-config.js` builds `HUB_FLYOUT` from it — which sub-pages appear in a hub's flyout is config plus whatever the installed modules declare, never hand-written markup (see Hubs). `js/view-lifecycle.js` exposes `runActiveViewCleanup`, which every view with timers or listeners must register with. Settings is one view with eight tabs (System, Keys, Agents, Skills, Modules, Users, Tools, Demo) backed by `/api/settings/*` and `/api/bitwarden/*`; Demo is pure static markup linking `/demo/index.html` in a new tab - a standalone presentation page that fetches the real `/index.html`, lifts the shell nodes listed in `demo/shell-contract.mjs` (guarded by `tests/test_demo_shell_contract.mjs`), paints every dynamic part from `demo/mocks/` and never calls `/api/`; every one of the eight ships a STATIC skeleton inside its slot in `index.html`, so the tab reserves its height at parse time - before `js/settings.js` is even fetched - and nothing jumps as the panels land one request at a time. Which means a renderer must never blank a slot it is about to fill: the `sett-loading` sentence the Agents, Skills and Modules panels used to write was shorter than the cards it stood in for, so it wiped the skeleton and reintroduced the jump it was meant to prevent. Those three now leave the slot alone (skeleton on a first paint, the previous cards on a repaint) and every exit path - success, empty and error - overwrites it. The Catalog section is the exception and paints its own skeleton grid, because it rebuilds its header on every render; each `ENV_SCHEMA` key carries a `kind` (`secret`/`config`/`system`); only `secret` and `system` render, `config` keys are edited in `.env` alone so there is never a second place for the same value to disagree.

`server.js` is one file split into labelled sections (`// -- Nazwa --`), each owning a route group; all JSON leaves through `jsonResponse` and all shared writes go through `withLock` plus tmp+rename.
