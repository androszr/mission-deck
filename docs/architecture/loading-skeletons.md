# Loading skeletons, infra banner and boot memos

Detail moved out of `CLAUDE.md` (section "Loading skeletons") so the file Claude Code loads on every turn stays under its size limit. `CLAUDE.md` keeps the rules; this file keeps the reasoning, the incidents and the measurements behind them. Add new detail HERE and at most one line to `CLAUDE.md`.

Settings and the onboarding wizard were the only two views that reserved their height before their data landed; every other one painted an empty box and jumped as each answer arrived. The layer that fixes that is STATIC markup in `index.html` plus `js/skeleton.js`, whose whole job is two rules a painter has to honour. A skeleton node carries `data-skel="1"`. A painter that rebuilds its container (`innerHTML =`, `replaceChildren`) drops it for free and needs nothing; the other two cases are what the module exists for. `clearSkeleton(root)` belongs on EVERY early return that paints nothing - a dead `/api/bitwarden/status`, a machine with no Bitwarden CLI, an activity chip with no token - because each of those is a final answer and a skeleton left standing there pulses for the rest of the session. `hasSkeleton(root)` guards the opposite mistake: a painter about to write something SHORTER than the skeleton must leave the box alone. That is the `sett-loading` bug generalised - `js/app.js` calls a view's renderer WITHOUT awaiting its `runInit`, so `renderGitlabActivityView` and `renderAcademyView` both run before their fetches settle, and the "Ladowanie..." sentence one of them wrote was shorter than both the skeleton and the table, so the page jumped twice instead of once. Both now hold the skeleton, and both have a release that does not depend on a happy answer: gitlab-activity paints a real error callout with a working "Refresh" when the FIRST load fails (a toast alone left the skeleton pulsing, and `_initedViews` means re-entering never refetches - so the renderer's no-data branch asks again), and Academy keys on `_stateLoading && !_stateLoaded` rather than on `_progress`, because a dead endpoint leaves `_progress` null for good. Reserve the REAL box, never an approximation: the dashboard's placeholders carry `.placeholder-hub-card` itself, and every Assets card height (141/206/242/260 px) and the Design System's three-row 165px toolbar were measured off the finished component, not guessed. `.ds-skeleton` paints `--body-quaternary-bg`, which IS the page background, so a bar sitting directly on the page rather than inside a white card needs the `--body-secondary-bg` override - without it the Assets and GitLab activity skeletons were laid out correctly and invisible. `_showLazyLoader` stands down on any section that ships a skeleton: it appends a 200px block in normal flow, so it would add its own height on top of the reserved boxes and cause the jump it is meant to hide.

Two things move the WHOLE grid and cannot be reserved with markup, so both remember their last answer and are stamped on `<html>` by `js/theme-boot.js` before any stylesheet applies - the same trick the theme already used, one axis over. The rail is 72px collapsed and 300px expanded and `.main`'s margin tracks it, but `_applyRailState` only runs once `js/app.js` has loaded, so the page painted in the wrong state and the entire grid slid 228px sideways on every load. The stylesheet now keys that geometry on `html[data-rail="collapsed"|"expanded"]` ALONE; the `.collapsed` / `.sidebar-collapsed` classes stay because JS queries them, and `_applyRailState` writes all three so they cannot disagree. The update banner is the other: it is `position: fixed`, but `.main` pads 68px -> 108px the moment `/api/app/check-update` answers, dropping every view 40px. Whether there IS an update is exactly what that request asks, so the last answer is remembered in `cockpit.updateBannerSeen` and the row is reserved from it - right on every load while an update sits un-applied, wrong exactly once, on the reload straight after updating. `_settleReservation` releases it on EVERY settled outcome INCLUDING the failures, because a check that cannot answer (offline, no token) would otherwise hold 40px of blank space all session. A second strip sits under the same rule: `#infra-banner` (`js/infra-banner.js`, decision and English copy in the pure `js/infra-banner-helpers.mjs`) paints from TWO independent readings and names only what is wrong - `vault` (the server holds no token: "Unlock the vault", button "Open vault"), `network` (tokens are loaded but the last call to GitLab failed on the network: "Turn on your VPN", button "Check again"), `access` (tokens are loaded and GitLab ANSWERED, but refused us - "most often the VPN is off. If it is on, renew the token", same button) and `both` - the taxonomy of `syncPrereqCallout` plus the one failure this cockpit really has that the first version could not see (below). The first version keyed on `hasSecrets` alone and told people to check the VPN, which hid the strip on exactly the machine it was written for: `bw` reads its LOCAL cache, so the vault opens without the VPN, the tokens land in the heap and survive a restart, the pill turns green, and the person whose clone had just died on "Could not resolve host" saw nothing (2026-09-14, from a screenshot). The vault half comes from `/api/bitwarden/status`, handed over by `_renderBitwardenButton` in `js/topbar.js` (boot and every `cockpit:secrets-changed`). The network half comes from `GET /api/infra/status`, a REGISTER read (`_infraNet`, verdict from the pure `infraNetworkState`): the server never probes for it, every GitLab call the process already makes reports its outcome - `_infraNoteFetch` in the identity lookup, the activity chip and the catalog GET (each hands over the response STATUS: a project-scoped 2xx is `ok`, 401/403 with the APP credential is `refused`, and everything else - a 404, a 5xx, and a 2xx from `GET /user` - says NOTHING: `/user` is user-scoped, the group's IP allowlist does not cover it, so a locked-out machine gets a 200 there and writing `ok` from it flapped the strip on every load; a 404 is never a refusal either, GitLab answers it for an absent `catalog.json` on a visible project too, and `classifyGitlab404` owns that resolution), `_infraNoteGitResult` in `_gitExecRepo`, `_gitP` and the clone (`classifyGitError === 'network'` is a failure, `auth-expired`/`no-access` on an `app:*` source is a REFUSAL through `_infraNoteRefused`, the same error on a DATA source says nothing, everything else says nothing; a killed transfer is a budget, not a dead host). The refusal axis is fed by the app's own credential ALONE (`_infraSourceIsAppCredential`: `app:*` git ops and `identity`), because any additional data source carries its own token and the catalog another - a 401 there proves something about THAT token, and a machine-wide strip pinned by one stale data token, or flapped by several parallel `fetch --prune` on every sync-modal open, would fire the recovery bus each time - because with the VPN down the relevant timeouts are 8 s to 45 s and a poll would slow every load for exactly the people already stuck. The top bar reads that register after the identity lookup (the first GitLab call of a load), after every `check-update` the update banner runs (`checkOnce`'s `finally`, a dynamic import of `refreshInfraStatus` - that `ls-remote` is the one call on a normal load that can write `refused`, and it settles after the first read, so without this the strip learned about the refusal from the 60 s poll a minute after the person had read the error), on its 60 s sync poll and on `POST /api/infra/recheck`, the ONE active probe behind "Check again" (the identity lookup past its memo, then `git ls-remote` on the APP repository through `_gitP` - the same call check-update makes, run LAST because the newest outcome is the verdict and `/user` alone cannot see an IP allowlist; skipped under `IS_TEST_MODE`, where `_appRepoUrl()` would resolve to the developer's real origin; without a token it probes nothing, since "no token" is the vault's story). The register has three axes (`okSeq`/`failSeq`/`refusedSeq`, newest wins) and four verdicts - `reachable`, `refused`, `unreachable`, `unknown` - because the second version had two and read a refusal as a success: this cockpit's GitLab is PUBLIC SaaS behind a group IP allowlist, so with the VPN down DNS and TLS keep working and GitLab answers 401 over git-over-HTTPS, which `classifyGitError` maps to `auth-expired` - and that landed on `reachable`, the strip stayed hidden, and the only thing the person saw was "The token was not accepted" in Settings > System (2026-09-16, from a screenshot). The strip written for the silent failure mode of an internal host missed the refusing failure mode of a public one. `refused` is its own kind and not a flavour of `network` because the two have different fixes and different lies - with the VPN up a refusal really is the token, and a `network` sentence would send that person after a VPN already on - so every `access` sentence names both, VPN first, the order `MODULES_CATALOG_NO_ACCESS_MESSAGE` and `js/app-update-errors.js` (whose four VPN-capable codes say the same) already use. The bad -> reachable edge (`infraRecovered`, from `unreachable` OR `refused`) is announced on the third bus, `js/infra-events.js` (`cockpit:infra-changed`): the top bar re-derives every token-painted slot and `js/update-banner.js` re-runs `check-update` - which without the VPN fails in silence and hides, so a person offline at boot never learned an update existed, which is how the first strip failed to reach the people it was for - and the server side of the same flip drops the three caches that memoised the outage (identity, activity count, MR counts). The X is remembered per KIND, not per session, so a vault strip dismissed in the morning cannot silence the network strip in the afternoon. A dead endpoint (`null`) on either side says nothing rather than blaming the other half; the Academy "ds-data is not cloned" callouts and the wizard's clone card read `getInfraNetwork()` and add "GitLab is not answering - turn on your VPN" on `unreachable` and "GitLab refuses the connection - check your VPN, and if it is on, renew the token" on `refused`, because that is why the clone will fail. It reserves its row the same way (`cockpit.infraBannerSeen` -> `html[data-infra-banner="reserved"]` in `js/theme-boot.js`, released on every settled answer) and the four visible/reserved combinations with the update banner are written out in `styles.css` rather than derived - alone 108px, both 148px with the strip at `top: 84px` - because the reserved states are CSS-only. It sits BEFORE `#app-update-banner` in document order so the update banner's expandable list paints over it. Covered by `tests/test_infra_banner.mjs`, the register block in `tests/test_server_helpers.mjs` and `tests/test_api_infra_status.js`. The module rail items are the third case and the one place the count itself is unknown: `js/rail-placeholders.js` reserves one row per module this browser saw last time. It is painted from `js/app.js` at module-evaluation time and NOT from `js/module-host.js`, which is reached through a dynamic import inside `boot()` - on a cold load that import is most of the wait the rows exist to cover (measured 1.4 s), so painting from there reserves nothing. `clearRailPlaceholders()` runs on every exit of `initModuleHost()` plus a `finally` around the import itself, which is an exit the loader cannot cover. Making the spacer work also needed `.sidebar-nav` to be a column flex container: as a block, `flex: 1 1 auto` on `.sidebar-spacer` grew to nothing and the pinned bottom group simply stacked under the last item, so every module rail item that landed pushed it 44px down. Measured with `PerformanceObserver` on `layout-shift`: dashboard, Academy, GitLab activity and all four Assets views now load at CLS 0. The module sync bar (see `js/data-events.js` above) reserves the same way: its skeleton and every painted state share one measured 50px height (`.ds-callout.msb-bar` in `styles.css` - a COMPOUND selector, because `css/ds.css` loads after `styles.css` and its `.ds-callout { min-height: 40px }` won on source order over a bare `.msb-bar`, which left the skeleton 10px shorter than the painted bar), so the bar never causes the jump it exists to prevent. Covered by `tests/test_loading_skeletons.mjs`.

The skeletons above fix the JUMP; what decided how long the bar kept pulsing was the server. Measured after the import-queue fix (topbar and banner started after the first `navigate`): view content painted at ~250 ms, and the last skeletons on screen were the Bitwarden pill (~1.7 s - `bw status` costs ~1.4 s per spawn and its memo lived 10 s, so every refresh more than 10 s after the last one paid it), the day-cycle pill (~1 s - eight parallel plaintext walks behind `GET /api/sync-overview`, memo 2 s) and the module sync bar (~3.4 s - it awaited `POST /api/sync-overview/refresh`, a `git fetch` per source with a 45 s per-source budget, BEFORE painting anything). Two changes, one rule each. Server side, `_createSwrMemo` (`server.js`, exported for `tests/test_server_helpers.mjs`) is the ONE stale-while-revalidate memo shape behind `_bwStatusMemo` and `_syncOverviewMemo`: inside the TTL every caller gets the one answer, inside the stale window (10 min for both) the last answer is handed back AT ONCE while one recompute runs behind it and replaces it, past that a caller waits; a recompute whose entry was invalidated while it ran is dropped, a failed recompute keeps the stale value, and both windows at 0 (test mode) reduce it to in-flight sharing. The bw memo keys on the session, and the side effect the status handler carried - dropping a session bw stopped honouring - moved INTO the compute, so a background probe performs it too. Anything that reads a row to DECIDE rather than to display re-reads past the memo: `handleSyncOverviewRefresh` invalidates unconditionally before answering (a source inside its 60 s fetch TTL moved no ref and so invalidated nothing), every write op still clears it through `_invalidateSyncModules`. `_warmBootMemos` runs both computes once at boot, after the handoff, so the first load after a restart finds the answers waiting. Client side, `paintModuleSyncBar` paints TWICE: first from what the server already knows (`GET /api/sync-overview` plus the per-module rows, labelled `Sprawdzam serwer…` through the `checking` option of the pure `moduleSyncBarState`, which caps a confident success at `info`), then again after the fetch; the sequence check catches a view left in between. Measured: every skeleton gone by ~250 ms on a refresh, the bar's first sentence at ~0.8 s and its checked one at ~1.7 s. Covered by the `_createSwrMemo` block in `tests/test_server_helpers.mjs`, the `checking` case in `tests/test_sync_center_helpers.mjs` and the two-paint pins in `tests/test_module_sync_bar.mjs`.
