## Hubs

The rail's hubs belong to the CORE, not to a module. `js/core-hubs.mjs` is the one place they are declared - eight rows, `id` ASCII and `label` English: `team` (Team), `activity` (Activity), `finance` (Finance), `initiatives` (Initiatives), `support` (Support), `knowledge` (Knowledge), `assets` (**Design**) and `apps` (Apps). `js/sidebar-flyout-config.js` is now a loop over that list rather than a hand-written map, and `index.html` carries one static rail item per row ABOVE `.sidebar-spacer`, so the pinned bottom group is just "Start here" and Settings. The markup cannot be generated at boot for the reason the Assets rule always stated - `bindSidebarItem` reads `HUB_FLYOUT[view]` synchronously as `js/app.js` evaluates - so `tests/test_core_hubs.mjs` is the gate that keeps markup, declaration and every copy of the id list identical. There are three copies by necessity and one test over all of them: the ESM declaration, `CORE_HUB_IDS` in `server.js` (CJS, and `validateModuleManifest` is sync, so it cannot import ESM) and the same literal in `scripts/new-module.js` (which mirrors `MODULE_ID_RE` and `RESERVED_MODULE_IDS` from `server.js` under the same stated rule - a scaffold must keep working while `server.js` is mid-edit). Every hub id is also a RESERVED module id, spread into `RESERVED_MODULE_IDS` rather than listed twice, because a module directory named `support` would shadow the rail item and take its hash route.

A module therefore does not create a menu entry; it puts PAGES in one. `sidebar.kind` has three values: `"page"` plus `sidebar.hub` (the normal shape - no rail item, one flyout row per view, labelled with the VIEW label), `"item"` (one view, own rail item) and `"hub"` (a multi-view module with a flyout of its own, still allowed - that is the escape hatch for somebody who needs a hub the core does not have and does not want to wait for one). `validateModuleManifest` checks `sidebar.hub` by NAME against `CORE_HUB_IDS`, not merely as a slug, and refuses `sidebar.hub` on any other kind, because the client's only answer to an unknown hub is to give the module NO menu entry - deliberately not a fallback rail item, since a fallback would break the very rule this split exists for at the moment a typo is least visible. `js/module-host.js` pushes into `HUB_FLYOUT[hub].items` IN PLACE (assigning a new array would drop Design's four core pages and any module loaded earlier) and `_isViewIdOccupied` now also refuses a view id equal to a hub id. The card in Settings > Modules reads the same shapes through `hubPageTarget()` / `isHubShape()` in `js/module-card.mjs` - which `js/module-host.js` IMPORTS rather than re-implementing, so the card can no longer promise a flyout the sidebar does not build. Seven of the eight hubs ship with no pages, so `_openHubFlyout` no longer returns early on an empty list: it renders a English empty-state line instead, and a hub item gets no collapsed-rail tooltip at all (the flyout's first line is already the hub's name, and the tooltip landed on top of that one sentence).

## Assets

`assets` is the one core hub that ships PAGES of its own (four), declared as `pages` on its row in `js/core-hubs.mjs`. Its id and its four `assets-*` view ids stay as they are while the rail reads "Design": the ids and the sections were all named before the hub was, and renaming them would move hash routes people have open. Deliberately NO `#view-assets` section, because `js/app.js` redirects a hub hash that has a section of its own. `tests/test_assets_hub.mjs` owns the four view triples; the hub itself (rail item, position, reserved id, no section) is covered by `tests/test_core_hubs.mjs`.

Four views, all reading data that is COMMITTED in this repository - there is no extraction pipeline here, unlike the cockpit these views were ported from, so an empty state says "the file is missing from the checkout" and never "run the generator". `assets-design-system` (`js/assets-design-system.js`) is the Figma component catalog, web and mobile: the global index plus the active platform's component index and tokens on entry, and one PAGE SHARD per card fetched only when that card scrolls into view (`IntersectionObserver`), because the index carries summaries and the faithful markup lives in the shards. Switching the platform must FETCH before it paints - the second platform is not loaded on entry, and painting first showed "no catalog for this platform" until the person left the view and came back. `assets-icons` and `assets-illustrations` are one engine, `js/assets-svg-catalog.js`: a manifest of `name -> {slug, file}`, a search box over a card grid, one delegated click listener for "Copy SVG" (1365 icons repaint on every keystroke, so per-card listeners are not an option), and a `displayName` hook - the illustrations manifest keys carry Figma's `name=` variant prefix, which is noise on a card but part of no id. `assets-mascot` (`js/assets-mascot.js`) is the mascot gallery and the only one with a route: `GET /api/assets/mascot` lists `assets/mascot/` (Pip, the original robot mascot), because a browser cannot read a directory. It does not share the SVG engine - the mascot SVGs are ANIMATED and must render as `<img>`, never inline, or every tile would run its own animation in the document. Every teardown (the observer, the delegated listeners, the back-to-top scroll handler) is registered with `registerViewCleanup` where the resource is created, never in `init`, because `init` runs once per session while cleanup is consumed on every exit. The back-to-top button lives INSIDE `#view-assets-design-system` rather than on `document.body`, so leaving the view hides it with the section and no `hashchange` guard is needed. Covered by `tests/test_assets_hub.mjs` and `tests/test_api_assets_mascot.js`.
